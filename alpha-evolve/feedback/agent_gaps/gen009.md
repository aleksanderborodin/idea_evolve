# Agent Gaps — Generation 9

## Gap 1: exploit_2 eval timeout — no time-budget guard in solutions

exploit_2/sol01.py runs optimization inside `entrypoint()` with no time limit. The evaluation
harness has a timeout (~600s or ~1200s), and the solution exceeded it. This is a recurring
pattern (also seen in gen004_explore_1_sol01).

**Impact:** Entire agent session wasted (no scored solution).
**Recommendation:** Agent prompts should mandate a time-budget guard in `entrypoint()`:
```python
deadline = time.time() + 500  # leave margin for eval overhead
if time.time() > deadline: break  # return best array found so far
```
This should be added to the agent templates (explore.md, exploit.md) as a required pattern.

## Gap 2: No plateau profiling before multi-element perturbation

exploit_1 discovered 13 autoconvolution positions within 1e-12 of the max AFTER attempting
and failing with triplets/quadruplets. If the plateau structure had been profiled first,
the agent could have:
1. Recognized that single-peak gradient is structurally inadequate
2. Implemented minimax gradient (idea_023) instead
3. Avoided wasting ~33k triplet and ~11k quadruplet trials

**Impact:** Wasted compute on approaches that couldn't work given the plateau structure.
**Recommendation:** Add a "profile plateau before perturbation" step to the standard
perturbation protocol. A simple diagnostic: count positions within 1e-10, 1e-11, 1e-12
of autoconv max. If >5 positions within 1e-12, single-peak gradient is unreliable.

## Gap 3: Momentum implementation performance assumptions were wrong

The brief stated "≥150 trials/s for base quadruplets" but exploit_2 achieved only 33-55 t/s.
The overhead from momentum chains and per-trial argmax computation was underestimated.

**Impact:** Trial count target (60k+20k+CD) was unrealistic for the time budget.
**Recommendation:** Brief performance estimates should come from profiling, not extrapolation.
When a brief claims a specific performance target, the agent should verify early (first 1000
trials) and adjust the plan if actual rate differs by >2x.

## Gap 4: No knowledge of N=5000 optimization floor before gen 9

The State of Affairs didn't note that N=5000 caps at C≈1.517, far above the frontier.
This information would have helped the Architect assess whether N=5000 LP experiments
were worth the compute investment.

**Impact:** Low — explore_2's diagnostic was the right experiment to run. But the result
should now be added to the State of Affairs.
**Recommendation:** Update State of Affairs with N-dependent floor: N=600 → ~1.504,
N=5000 → ~1.517, N=30k → ~1.503 (from gradient + CD). Note that N=30k is paradoxically
better than N=5000 because the initial array (TTT-Discover) was produced by LP-guided
methods, not gradient descent.

## Gap 5: batch_trial_evaluator helper created but not integrated

experimentator_1 built batch_trial_evaluator.py with 46x speedup. No gen 9 agent used it
because it was created in the same generation.

**Impact:** Low for gen 9 (helper wasn't available to agents). High priority for gen 10
— all perturbation agents should use it.
**Recommendation:** Architect brief for gen 10 should explicitly list batch_trial_evaluator
as an available and required helper for perturbation-based agents.

## Gap 6: Checkpoint arrays from exploit_2 are unscored

exploit_2 saved 5 checkpoint arrays (ckpt_quad_1-5.npy) representing partially-optimized
solutions. These are potentially valuable but unscored. A simple wrapper would evaluate them.

**Impact:** Medium — these may contain improvements that are invisible to the pipeline.
**Recommendation:** A gen 10 agent should load ckpt_quad_5.npy (the most recent), verify
with compute_c_f64, and if improved over gen 8 best, bake and submit as a scored solution.

## Gap 7: Inconsistency between exploit_1 and explore_1 results

exploit_1 found 0 triplet improvements after ultra-fine CD, while explore_1 found 150 triplet
improvements starting from the gen 8 best (which only had standard-delta CD). This is
consistent with pattern_020 (ultra-fine CD subsumes triplets), but the implication for the
optimal optimization sequence hasn't been tested: does standard CD → triplets → ultra-fine CD
outperform direct ultra-fine CD?

**Impact:** If the sequence matters, the optimal protocol may produce a better result than
either approach alone. Currently untested.
**Recommendation:** Explicit A/B test:
- Path A: gen 8 best → ultra-fine CD (as exploit_1 did)
- Path B: gen 8 best → triplets → ultra-fine CD
Compare final scores to determine if ordering matters.
