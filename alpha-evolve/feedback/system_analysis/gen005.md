Generated by: System Critic

## Overall Assessment

Generation 5 was the strongest generation to date from a pipeline execution standpoint:
no agent timeouts, all objectives completed, 100% output coverage, and the first
milestone of agent-driven improvement over a published solution. The analysis below
identifies the remaining problems — several are urgent, none are catastrophic.

## Pipeline Problems

### [CRITICAL] Consistency Review has not run for two generations

**Evidence:** The State of Affairs is still dated gen 3 (frontmatter: `generation: 3`).
Both gen 4 and gen 5 system critics flagged this as Priority 1. The gen 5 Architect noted
it and worked around it by including explicit dead-end notices in briefs. Four gen 5 agents
independently flagged the SoA as stale. The recommendation that the Consistency Review run
before gen 5 (Priority 1 in gen 4 recommendations) was not followed.

**Root cause (hypothesis):** Either the Consistency Review runs but its outputs are not
being moved to the canonical knowledge path, or it is not being triggered at all. The
orchestrator triggers it every 3rd generation or on strategic shift. Gen 4 returned
`strategic_shift: false`; gen 5 returned `strategic_shift: false`. Gen 3 returned
`strategic_shift: true`, which would have triggered the review. If that review ran and
produced output, the SoA was not updated from those outputs.

**Impact:** The stale SoA costs every agent 3–5 turns reading and mentally correcting
stale priorities. The gen 5 Architect explicitly noted the SoA still recommends warm-start
smooth-max Adam as Priority 1 — a strategy closed by gen 4's pattern_007. For gen 6, if
the SoA is STILL gen 3, the Architect's brief-writing will require extraordinary amounts
of inline override text, and agents that trust the SoA will be misled.

**Severity: CRITICAL** — two generations of staleness. Risk of regression in gen 6 if
the Architect session is shorter or less careful.

### [CRITICAL] exploit_2/sol01 has eval_time = 792.6 seconds

**Evidence:** `population/gen005/exploit_2/sol01.score` contains `"eval_time_s": 792.5655`.
This solution re-runs coordinate descent optimization at evaluation time rather than baking
the final array into the solution. The pipeline's evaluation system caches by content hash,
so this is a one-time cost for this exact file — but the solution is now in the ranking
and any operation that needs to re-evaluate it (different evaluate.py, fresh clone, cache
miss) will take 13 minutes.

**Root cause:** exploit_2's debrief explicitly states: "The background run to save the
array was killed before completing." The agent knew this was a problem but could not fix
it within the session. There is currently no pipeline mechanism to detect or flag solutions
with excessive eval_time and prompt re-submission of a baked version.

**Impact:**
1. The solution at C=1.5028628894 (new best) cannot be safely re-evaluated without a 13-minute wait.
2. Any agent that loads this solution for warm-start (which multiple gen 6 strategies require)
   will spend most of its turn budget waiting for entrypoint() to return.
3. The `load_cached_solution` helper doesn't exist, so agents cannot extract the array without re-running.

**Severity: CRITICAL** — the pipeline's best solution is in a degraded state. A baked-array
replacement must be created before gen 6 agents use it.

### [MODERATE] Float32 helpers produce incorrect results for micro-optimization

**Evidence:** Both exploit_1 and exploit_2 reported that `helpers/sensitivity.py` and
`helpers/core.py` use float32, which introduces ~1e-6 precision error. For solutions
optimized to C~1.5029 (where improvements are at the 1e-8 level), this renders float32
as an oracle completely unreliable. exploit_2 explicitly measured: the top-20 most sensitive
elements are DIFFERENT between float32 and float64 — element 48 ranks #1 in float32,
element 3236 ranks #1 in float64.

**Implication for pattern_007:** Pattern_007 ("smooth-max Adam cannot improve published
solutions") was established using float32 accept/reject decisions. The evidence base for
this pattern may be tainted. The evaluator recommends re-testing with float64.

**Root cause:** When the three helpers were created (inv_softplus.py, sensitivity.py,
interpolation.py), they were not created through the experimentator workflow — the Architect's
gen 5 report notes they "exist but weren't created through the experimentator workflow."
There was no correctness review against validate.py's float64 computation.

**Severity: MODERATE** — currently every agent that uses these helpers for optimization
(not just sanity checks) gets wrong guidance. This contributed to exploit_1's null result.

## Missing Capabilities

### [CRITICAL] No `compute_c_f64` helper

The single most-requested helper across gen 5. Both exploit agents independently reimplemented
float64 compute_c from scratch. exploit_2's reimplementation enabled the first agent-driven
improvement. exploit_1 could not perform float64 coordinate descent effectively without it.

This helper is trivially implementable (copy validate.py's numpy computation), yet the gap
persisted through five generations. Four agents across two generations have explicitly requested it.

**What's needed:** `problem/helpers/compute_c_f64.py` — numpy float64 implementation matching
validate.py exactly. Document precision: matches float64 oracle within 1e-15.

---

### [MODERATE] No `autoconv_analysis` helper

exploit_1 manually reimplemented autoconvolution peak analysis (which (i,j) pairs produce
the peak, which constraints are near-tight). This is fundamental to any LP-based refinement
and to understanding whether coordinate descent will succeed. The LP-based approach is now
the highest-priority unexplored strategy, and it requires this analysis.

---

### [MODERATE] No mechanism to flag or replace high-eval-time solutions

The pipeline has no automated check for `eval_time_s` in .score files. The threshold for
"acceptable" evaluation time is never stated, so agents don't know when they must bake arrays.
A solution at 792.6s is in the population with no warning to downstream agents.

**What's needed:** Finalize phase should flag solutions with `eval_time_s > 60` and either
(a) reject them from rankings, or (b) add a visible warning in the population summary.
The Architect brief template should include: "Never submit solutions that re-run optimization
at eval time — always bake the final array."

## Prompt Problems

### [MODERATE] Agent briefs do not warn against compute-at-eval-time solutions

The evaluator flagged this directly: "Explicitly flag eval_time > 60s solutions."
This is the second time this class of bug has appeared (exploit_1 gen 4 had a similar issue).
The exploit/full agent templates should contain a mandatory rule:

> "Your final solution must bake the optimized array as a literal in the entrypoint() function.
> Never re-run optimization inside entrypoint(). The evaluator times the entrypoint call;
> solutions that re-run optimization will have eval_time > 100s and will be flagged invalid."

## Knowledge Quality Issues

### [MODERATE] Pattern_007 evidence base is tainted by float32

Pattern_007 asserts that smooth-max Adam cannot improve published solutions. This was
established in gen 4 using float32 accept/reject decisions. exploit_2's gen 5 work revealed
that float32 can produce false accept/reject decisions (a "success" that validate.py
rejects as equivalent or worse). Until pattern_007 is retested with float64 throughout,
its confidence level should be reduced.

**Recommendation:** Mark pattern_007 as `disputed` and add: "Evidence from gen 4 used
float32 oracle which has ~1e-6 precision — insufficient for accept/reject at this optimization
level. Re-test required."

### [MINOR] idea_005 and idea_011 not yet archived

The evaluator recommended archiving idea_005 (Regularization approaches, confidence 0.4,
never tested in 5 generations) and idea_011 (Lion optimizer, confidence 0.35, stale since
gen 1). These ideas consume idea budget and fragment agent attention without contributing
information. The Consistency Reviewer would handle these if it ran.

## Experiment Gaps

### Most Valuable Untested Experiments (priority order)

1. **Float64 re-test of pattern_007** — is smooth-max Adam truly dead, or was it blocked
   by float32 noise? This is the single highest-leverage question. If float64 smooth-max
   works, it reopens the entire warm-start strategy.

2. **LP-based refinement** — both exploit agents named this as the only method ever proven
   to improve solutions at this quality level. No agent has implemented it. The barrier
   is engineering complexity (LP solver setup), not algorithm uncertainty.

3. **Extended float64 coordinate descent (baked array)** — exploit_2 found 116 improvements
   in 10 passes of top-500 elements. Extending to top-2000, finer deltas, and 30 passes
   is a direct continuation of the only method that has worked. Low risk, high expected value.

4. **Warm-start from research_1 N=600 arrays** — five new warm-start targets at C=1.5053
   to C=1.5032 at N=600 (directly pipeline-compatible). These have not been tried with
   smooth-max Adam. If float64 re-test confirms pattern_007, these targets are at the
   same resolution as gradient-descent solutions and may be in different basins.

5. **Bulk-zero LP residuals** — exploit_2 found that many elements in TTT-Discover are at
   ~1e-13 (LP solver residuals). Zeroing ALL such elements simultaneously may yield a larger
   improvement than element-by-element coordinate descent.
