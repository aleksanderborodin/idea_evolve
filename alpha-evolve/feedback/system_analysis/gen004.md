### [CRITICAL] Brief over-specified SA computation budget without timing context

**Evidence:** explore_1 implemented a correct SA protocol (sigma=0.05*std, cold inner optimizer,
calibration loop) but the brief specified "500-1000 SA iterations" without flagging that this
translates to 600k gradient evaluations at 1.8ms/step = ~18 minutes. The evaluation timeout
(~540s) killed the process. explore_1's debrief: "The brief's '500-1000 SA iterations' was
aspirational, not accounting for time constraints."

**Root cause:** The brief provided iteration counts without step-time estimates. At gen 4's
knowledge level, timing data for N=23 optimization was available (from gen 3's timing records
and exploit_1's benchmark of 1.8ms/step at N=1319). The brief should have translated
"500 iterations × 300 steps × 4 seeds = 600k steps × ~1ms/step = 600s → exceeds timeout."

**Severity: Critical.** One of four agent slots produced zero usable output. The SA approach
is still the most promising untested optimization method; this is the second consecutive
generation where SA timed out.

### [MODERATE] Exploit brief recommended cubic spline — wrong for sparse arrays

**Evidence:** exploit_2 used cubic spline to upsample the AlphaEvolve 1319-element array to
N=2000. The result (C=1.5159) was 0.0127 worse than baseline. exploit_2 debrief: "The brief
suggested cubic spline interpolation. This is inappropriate for the AlphaEvolve array's
sparse structure — it creates oscillations and negative values in the near-zero gap regions."

**Root cause:** The cubic spline recommendation was in the brief (presumably based on prior
knowledge). The AlphaEvolve array's multi-peaked sparse structure (near-zero valleys, large
spikes) makes cubic splines generate artifacts. Piecewise-linear or zero-preserving
interpolation would be correct.

**Severity: Moderate.** The second exploit slot was also wasted on a predictably bad approach.
However, "cublic spline interpolation destroys sparse solution structure" is now a confirmed
dead end (coverage matrix updated), so the compute wasn't entirely wasted.

## Missing Capabilities

### [HIGH] No computation budget estimator in briefs

Three consecutive generations (2, 3, 4) have had SA-related agents exceed timeout. The root
cause is always the same: iteration count × steps_per_iter × time_per_step > timeout, but
the agent computes this only after writing the full solution. A brief section with pre-computed
timing should be standard:

```
## Compute Budget Reference
- N=23 Adam step: ~0.5ms (JIT warm, from gen4 timing.json)
- N=600 Adam step: ~1.8ms (from exploit_1 gen4 benchmark)
- Timeout: 540s (from metrics.yaml eval_time_budget)
- Max viable: 540s / 1.8ms = ~300k steps at N=600; or ~1M steps at N=23
```

This would prevent explore_1's 600k-step overrun. It requires the orchestrator to include
timing data from `history/timing.json` directly in explore/exploit briefs (not just in the
Architect prompt).

### [HIGH] No projected gradient descent helper

Both exploit_1 and exploit_2 identified projected gradient descent (optimize f directly with
`clamp(f, 0, inf)` non-negativity projection, bypassing softplus parameterization) as the
highest-priority next experiment. No agent implemented it because the softplus parameterization
is baked into the solution template. A helper that:
- Loads a solution's f array
- Provides a JAX-compatible loss function differentiating C w.r.t. f directly
- Projects gradient steps onto the non-negative orthant

...would enable multiple agents to attempt this in gen 5 without redundant re-implementation.

### [MODERATE] No sensitivity map helper

All four gen 4 agents mentioned wanting ∂C/∂f[i] for all elements. This is a 5-line JAX
computation (`jax.grad(compute_c)(f)`) but three agents wished it existed as a helper.
Providing it as a reusable function would unlock sensitivity-guided experiments across
multiple agents simultaneously.

### [MODERATE] No inv_softplus helper with near-zero handling

All exploit agents manually implement `inv_softplus` with varying epsilon handling. The
softplus inverse at near-zero values (f ≈ 1e-7) requires careful treatment to avoid mapping
to large negative values (~-16) that freeze Adam gradients. A single canonical helper would
prevent per-agent reinvention and potential bugs.

## Prompt Problems

### [MODERATE] Architect brief can't adapt exploit targets to research discoveries

The fundamental sequencing limitation: briefs are written before agents run. Even with
sequential parallel_groups, the Architect can't know what research_1 will find before writing
exploit briefs. The current mitigations (listing research_1 output paths in exploit briefs)
don't go far enough.

**Fix:** Exploit briefs should contain explicit dynamic-update logic:
> "Check population/gen005/research_1/ before starting. If research_1 produced a solution
> with score below {current_best}, warm-start from that array instead of best.py."

This is template-level language the Architect can write without knowing research_1's result.

### [MINOR] Solution templates assume softplus parameterization

The solution template structure (raw_params → softplus → f) is baked into all solution
examples. Published solutions have native f arrays that get damaged by the
inv_softplus → softplus round-trip (especially near-zero elements). Agents reinvent
workarounds each generation. A template variant for direct f-space optimization would
save significant agent turns.

## Experiment Gaps

### [CRITICAL] Projected gradient descent never attempted

Five separate agents across gens 3-4 have identified this as the highest-priority experiment,
but no one has implemented it. The softplus parameterization is the root cause of all
warm-start failures. Bypassing it via direct f-space optimization + non-negativity projection
is the natural fix. This needs a dedicated agent slot in gen 5.

### [HIGH] Coordinate descent on TTT-Discover 30k array

Gradient-free, parameterization-agnostic, zero implementation risk. For each index i, try
f[i] ± δ for δ in {0.001, 0.01}, keep improvements. Trivially parallelizable by element
range. Nobody has attempted this despite three agents recommending it. With 30k elements,
even 100-element coordinate sweeps could identify optimizable regions.

### [HIGH] Calibrated SA at N=23 (correct method, reduced budget)

explore_1's implementation was technically correct. It failed only on budget. With 2 seeds
× 100 SA iters × 300 steps + 5k coarse steps + 10k fine steps ≈ 60k gradient evals → ~60s.
Well within timeout. This should be gen 5's top explore experiment.

### [HIGH] Extract and evaluate Cell 47-58 intermediate arrays

research_1 mapped all six intermediate arrays in the AlphaEvolve notebook (cells 47, 50, 52,
54, 56, 58 at C=1.5053→1.5033) but extracted none. Cell 47 (N=600, C=1.5053) and Cell 50
(N=600, C=1.5040) are at our gradient pipeline's native resolution. They can be warm-started
directly without interpolation artifacts.

### [MODERATE] Sensitivity-guided coordinate refinement

Compute ∂C/∂f[i] for all 30k elements using JAX autodiff (fast with FFT-based compute_c).
Identify top-100 most sensitive elements. Apply coordinate descent only to those elements.
Five agents across three generations have suggested this; it remains untried.

### [MODERATE] Retrieve AlphaEvolve V2 array (1.50317)

The SOTA table shows AlphaEvolve V2 at 1.50317. Our best.py shows 1.5031635 which matches
ThetaEvolve's 1.50313 (per research_1's analysis). The AlphaEvolve V2 array may be slightly
different (1.50317 vs 1.50316 rounded differently). Worth checking the AlphaEvolve repo for
an explicit V2 array file.

### [LOW] Reimplement TTT-Discover LP method

TTT-Discover uses LP with near-tight constraint heuristic (focus on top-K positions where
convolution is largest). This is a fundamentally different approach from smooth-max Adam or SA.
If we can reimplement even a simplified version, we could run it at native resolution without
needing to retrieve external arrays. High complexity, potentially high payoff.
