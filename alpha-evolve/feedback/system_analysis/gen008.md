### [MODERATE] incremental_update allocation overhead causing 15x agent performance degradation

**Evidence:**
- exploit_1 gen 8: "First version too slow: calling `incremental_update()` per delta
  allocates a 60k array each time. With 30000 elements × ~48 deltas = 1.44M allocations
  per round. Estimated 19 min/round." This forced fallback to a simpler, less complete run.
- exploit_2 gen 8: "internal `np.arange(M, dtype=np.int64)` allocation on every call is
  a significant overhead." 150 trials/s observed vs theoretical ~220.
- explore_1 gen 8: "~112 trials/s" — Python loop bottleneck.
- Multiple agents in gens 6, 7, 8 have flagged this issue.

**Root cause:** `incremental_update` allocates a new array on every call. For trial-and-reject
workflows (test many deltas per position, accept one), this means O(N_trials) allocations
where most are discarded. An in-place or trial-only variant would avoid almost all allocation.

**Impact:** exploit_1's full interleaved protocol (coord → triplet → quadruplet → repeat)
was abandoned due to this bottleneck. This is the highest-priority unrun experiment.

**Severity: MODERATE** (blocks the most important gen 9 experiment, has been flagged 3+ gens)

## Missing Capabilities

### [HIGH] No vectorized batch trial evaluator

All perturbation methods (coord descent, triplets, quadruplets) currently evaluate candidates
in a Python loop at 100–220 trials/s. Multiple agents (explore_1, exploit_1, exploit_2 gen 8;
exploit_2 gen 7) have requested a helper that:
- Accepts K candidate index-sets simultaneously
- Computes all gradient directions as a matrix operation
- Evaluates all step sizes via broadcasting
- Returns the best improving candidate

**Expected speedup:** 10–50x (1000+ trials/s). This would transform the full interleaved
multi-order cycle from a session-busting 19-min/round problem into a 1–2 min/round problem.

### [HIGH] No general k-plet perturbation module

Every generation re-implements triplet/quadruplet search from scratch with variations. The
pattern is now stable (gradient projection onto sum=0 hyperplane, integral-preserving).
A module parameterized by k would:
- Eliminate per-agent reimplementation
- Enable direct quintuple and sextuple experiments
- Standardize strategy selection and improvement logging

### [MEDIUM] No init_smooth_f(N) helper

explore_2 identified the need: to test LP at N=5000, you need a near-optimal N=5000
solution, which requires running gradient descent from scratch. Without a standard initialization
function, every agent reinvents the same Adam + smooth-max setup. This is the same situation
that led to the coordinate_descent helper request.
