# System Analysis — Generation 7

System Critic review. Generation 7 produced 4 genuine improvements and 3 unchanged baselines.
New best: C = 1.5028628689 (explore_1, triplet perturbation). Coordinate descent confirmed
converged; LP confirmed fundamentally blocked; triplet perturbation established as new frontier.

---

## Pipeline Problems

### [MODERATE] Experimentator helpers arrive too late to benefit same-generation agents

**Evidence:** The experimentator delivered `incremental_autoconv_update`, `cross_convolution_f64`,
and `lp_matrix` in gen 7, simultaneously with solution agents. All three coord descent agents
(exploit_1, exploit_2, full_1) reimplemented `incremental_autoconv_update` independently from
scratch. The `lp_matrix` helper was available but never used by full_1, which reimplemented LP
construction anyway.

**Root cause:** The experimentator runs in the same parallel group or at the same time as solution
agents. Helpers built in generation N cannot be used until generation N+1. This is a structural
timing issue in how the manifest is organized.

**Impact:** 30-60 minutes of agent work wasted per generation when a helper exists but arrives
simultaneously. In gen 7, three agents each spent ~15-20 minutes reimplementing the same O(N)
incremental formula. Total waste: ~45-60 minutes of billable agent time.

**Recommendation:** The experimentator should always run in an earlier parallel group than solution
agents, OR the Architect must schedule "experimentator-only" generations when new helper needs
are identified. If the same helper is requested by two or more consecutive generation's agents,
it must be built BEFORE those agents launch.

### [MODERATE] Coord descent convergence inconsistency across agents — non-reproducible results

**Evidence:** Three independent agents ran coordinate descent from the same starting point
(gen006/exploit_1/sol01.py, C=1.5028628724712894) and found wildly different improvement counts:
- exploit_1: 6551 improvements over 6 rounds
- exploit_2: 156 improvements over 3 rounds
- full_1/sol04: 257 improvements over 2 rounds

All three are valid improvements, but the 40x discrepancy in improvement counts indicates
non-standardized delta grids, scan orderings, or floating-point handling. exploit_1 used a
combined absolute+proportional+zeroing delta grid; exploit_2 and full_1 used primarily absolute grids.

**Impact:** Convergence claims become unreliable. When exploit_1 says "6 rounds, 6551 improvements,
converged" and exploit_2 says "3 rounds, 156 improvements, converged," it's unclear what the
true coordinate-wise minimum is or how many improvements remain. Agents reading these reports
may draw conflicting conclusions about the remaining headroom.

**Recommendation:** Standardize coordinate descent in the `coordinate_descent.py` helper (requested
by 4 agents in gens 6-7). A canonical delta grid and scan order would produce reproducible results
and allow meaningful comparison across generations and agents.

**Evidence:** `history/score_progression.md` shows:
```

| 5 | 1.502863             |
```

Gen 7 will similarly display as `1.502863`. Actual improvements: gen 5: -8.82e-9, gen 6: -2.58e-8,

**Impact:** Architects reading the progression table see a 4-generation stall and may pivot strategy

**Recommendation:** This is an orchestrator code change to `_update_score_progression()`. Change
format to use 10 decimal places or add a "delta" column showing scientific notation. One-line fix.

### [MINOR] LP sent three times in gen 7 with no plateau pre-check

**Evidence:** full_1 submitted three LP-based solutions (sol01, sol02, sol03), all returning
unchanged C=1.5028628725 (complete failures). The plateau structure (6500 near-max points) was
not known at brief-writing time but could have been diagnosed in 1 tool call at the start of the
session. Instead, full_1 spent multiple turns implementing LP at three different configurations
before diagnosing the root cause in sol04.

**Impact:** 3 wasted solution slots and significant agent time (~45 turns) on approaches that
full_1 itself concluded were "fundamentally blocked." sol04 (extended coord descent, 257
improvements) was the profitable approach but was run last, after budget was depleted.

**Recommendation:** Future LP briefs should mandate: "Before implementing LP, run
`tight_constraint_indices(f, epsilon_rel=1e-7)` and report the count. If count > 500 at N=30k,
LP at full resolution is infeasible. Proceed to coordinate descent instead." This pre-check takes
<1 second and would have redirected full_1 immediately.

## Missing Capabilities

### [MODERATE] No `coordinate_descent.py` helper — requested by 4 agents across 2 generations

**Evidence:** The following agents have explicitly requested a standardized coordinate descent helper:
- gen6 exploit_1: "incremental_autoconv.py would be extremely valuable"
- gen7 exploit_1: "Missing helper: incremental autoconv update"
- gen7 explore_1: "helpers/coord_descent_round.py — a full round of single-element coord descent"
- gen7 evaluator: "`coordinate_descent.py` — a full coord descent loop using incremental_update"
- gen7 experimentator: "coordinate_descent.py is a natural complement to these helpers"

The helper is the most-requested deliverable in the pipeline's history. It would encapsulate the
delta grid, scan order, and incremental update in a single reusable function.

**Impact:** Every future coord descent agent reinvents the same loop. Worse, different
implementations produce incomparable results (see convergence inconsistency above). Standardization
would improve reproducibility AND save 15-30 minutes per agent.

**Recommendation:** Assign experimentator to build `coordinate_descent.py` as the FIRST task in
gen 8 AND run it in an earlier parallel group than solution agents. Priority: Critical.

---

### [MODERATE] No triplet strategy logging — 160 improvements with no attribution

**Evidence:** explore_1 rotated 4 selection strategies (random nonzero, large+small+random,
neighbor triplets, fully random) but logged only total improvements (160 over 60k trials). The
agent_gaps report (Gap 1) explicitly calls this out.

**Impact:** The most productive strategy is unknown. If mass redistribution (large→small) produces
80% of improvements, gen 8 triplet agents should use that strategy exclusively. Without the
breakdown, gen 8 triplet work will be less efficient.

**Recommendation:** Future triplet agent briefs must mandate per-strategy counters. Specifically:
"Log `n_improvements_by_strategy = {0: 0, 1: 0, 2: 0, 3: 0}` and report the breakdown in your
debrief." This is free instrumentation that should have been in the gen 7 explore brief.

### [MINOR] Autoconv plateau diagnostic not yet a helper

**Evidence:** The autoconvolution plateau structure (6500 near-max points at eps=1e-7, 15384 at
eps=1e-10) was discovered independently by exploit_1 and full_1. It's now documented in
pattern_013, but computing it requires 3-5 lines of code that every future LP-exploration agent
will write from scratch. The experimentator's gen 7 brief included `tight_constraint_indices`
inside `cross_convolution_f64.py`, which is the right function — but agents need to know to use
it and understand what the count means.

**Recommendation:** Add a diagnostic note to the helpers README: "`tight_constraint_indices`
with `epsilon_rel=1e-7` on the current best array returns ~6500. Any LP approach must either
include all these constraints (1.5GB matrix at N=30k) or use reduced resolution. Check this
before designing any LP experiment."

## Prompt Problems

### [MODERATE] exploit_2 brief directed resources to AlphaEvolve arrays despite different-basin evidence

**Evidence:** exploit_2's brief apparently directed it to "explore AlphaEvolve arrays" as a
meaningful experiment. The actual results: N=600 had zero improvements (already coordinate-wise
optimal); N=984 and N=1444 converge to C~1.5035, which is 6e-4 above the current frontier.
exploit_2's own debrief notes: "Start with the current best immediately instead of spending time
on AlphaEvolve arrays that are 6e-4 away from the frontier. They are clearly in a different,
worse basin."

**Impact:** exploit_2 spent its first ~40% of session time on arrays confirmed to be in an
inferior basin. The useful output (156 improvements on TTT-Discover, attempt 4 in the debrief)
was produced only after the AlphaEvolve detour.

**Root cause:** The brief did not convey basin separation clearly enough, or overweighted the
"different basin might yield different improvements" hypothesis relative to its actual probability.
gen 6 coord descent on the same array (full_1) found zero LP improvement — the AlphaEvolve arrays
have been confirmed in a worse basin since gen 5.

**Recommendation:** Remove AlphaEvolve arrays from exploit briefs until a specific recovery
strategy (e.g., triplet perturbation to escape basin, or genetic crossover) is designed. The
time-to-benefit from AlphaEvolve arrays is clearly much lower than TTT-Discover work.

## Resource Issues

### [MODERATE] Four generation "eggs in one basket" — all frontier agents on TTT-Discover 30k

**Evidence:** The Architect's own report (Strategic Risks, #1) notes: "All eggs in the TTT-Discover
basket. 4 of 5 agents work on or derive from TTT-Discover 30k. If there's a fundamental limit
to coordinate descent on this array, gen 7 is a near-wipeout."

**Impact:** This risk materialized partially — coordinate descent converged faster than expected.
The only surviving productive approach (triplets, explore_1) was by one agent. Had the triplet
approach failed, gen 7 would have been three coord descent convergences and three LP failures:
7 valid solutions, 0 meaningful progress.

**Assessment:** The Architect identified this risk explicitly, so it was a known bet. However,
the lack of divergent exploration means any generation where the primary frontier technique
saturates results in minimal information gain.

**Recommendation:** For gen 8, ensure at least one agent explores a genuinely different
approach (e.g., LP at intermediate resolution as a dedicated analytical task, or quadruplet
perturbation, or generating a new starting array at N=10000 or N=50000). The main TTT-Discover
work should not consume more than 3 of 4+ agents.
