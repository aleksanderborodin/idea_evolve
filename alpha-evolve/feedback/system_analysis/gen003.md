## 1. Pipeline Problems

### [CRITICAL] Research findings cannot feed intra-generation coding agents

The research agent and all coding agents ran in the same parallel group (or equivalent). research_1 retrieved C=1.5032 — the highest-impact result of the generation — but explore_1, explore_2, and exploit_1 had no access to it while working. The `parallel_groups` mechanism in `manifest.yaml` supports sequential groups, but all Gen 3 agents appear to have run in a single group.

**Evidence:** explore_1 debrief: "I didn't know about population/best.py." exploit_1 debrief: "Without the actual raw_params from gen002 sol03, I couldn't warm-start." research_1 retrieved the array but stated "warm-starting is the exploit agent's job." No agent warm-started from C=1.5032.

**Impact:** The #1 highest-leverage experiment of the generation was completely skipped. The three coding agents consumed full compute budgets running approaches with no realistic path below 1.509.

**Fix:** The Architect should place research agents in parallel_group 1 and exploitation agents (especially exploit) that depend on their output in parallel_group 2. This is explicitly supported by the manifest format.

## 2. Missing Capabilities

### [CRITICAL] No raw_params serialization alongside solutions

Agents optimize in raw_params space, convert to f-values, save f-values, discard raw_params. This means warm-starting from a prior solution requires re-deriving raw_params via `inv_softplus(f)`, which introduces reconstruction error and may not recover the exact prior basin.

**Evidence:** exploit_1 debrief: "My re-derived seed 0 gave 1.509358, while gen002 sol03's best was 1.5091 — suggesting different seeds or more optimization steps found the better basin." agent_gaps/gen003.md Gap #3.

**Fix:** Agents should save `sol01_raw_params.npy` alongside `sol01.py` when they know a future exploit agent will need the exact basin. Alternatively, `evaluate.py` could save the raw_params array to the `.score` JSON sidecar.

---

### [MODERATE] No SA calibration utility

Three SA implementations across Gen 2-3 (explore_2 gen002, explore_1 gen003 ×3) all failed due to sigma/metro_temp calibration. The Gen 2 System Critic recommended adding SA acceptance rate logging; this was not implemented.

**Evidence:** explore_1 all solutions 1.5148–1.5169 with 60-100% acceptance rates. exploit_1 Gen 2 report had same calibration issues. Gen 2 system_recommendations.md Priority 5: add SA acceptance rate logging — not yet in helper.py.

**Fix:** Add a `calibrate_sa_temperature(func, initial_point, sigma, n_samples=20)` function to `problem/helper.py` that returns the expected acceptance rate. Document the target range (20-40%) in the function docstring. SA implementations without a calibration phase should be considered incomplete.

### [MODERATE] SA sigma formula in agent templates is scale-inappropriate

The sigma formula `0.3 * mean(|f|)` (cited in explore_1's brief) is incorrect for the scale of typical f-value magnitudes at coarse N. At N=80, mean(f) ≈ 20-40, making sigma = 6-15, which randomizes the entire solution rather than making a small perturbation.

**Evidence:** explore_1 debrief: "The formula may assume f values are in [0,1], not [0,40]." explore_1 observations: "sigma = 0.35*mean(softplus(raw)) — but mean(f) was large (20-40) making sigma=7-15."

**Fix:** Replace with sigma = `0.05 * mean(|f|)` and add a cap: `sigma = min(sigma, 1.0)`. Better: sigma should be specified as a fraction of `std(raw_params)` at the coarse scale before optimization, not after.
