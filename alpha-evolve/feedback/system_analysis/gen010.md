## 2. Missing Capabilities

### 2a. No Solution State Metadata

Agents repeatedly discover they are starting from a solution that has already had
ultra-fine CD applied — but they cannot tell this from the file. Multiple agents this
generation and last generation wasted triplet/quadruplet phases because they assumed
the starting point was "standard-CD-only."

A sidecar file (e.g., `sol01.meta.json`) recording which optimization stages have been
applied would allow the Architect to brief agents accurately and allow agents to skip
phases that are already exhausted.

**What would help:** Evaluator or finalize phase writes `optimization_history` field to
the `.score` JSON, or a separate `.meta` sidecar. Agents check this before investing
time in multi-element phases.

---

### 2b. No Multi-Trajectory Competition Infrastructure

exploit_1 noted that different random orderings through the 30k-element space find
different CD improvement paths — its baked solution was better than the dynamic run.
The evaluator proposed multi-trajectory competition (5 independent runs × 100s each,
then continue the best for remaining 400s). No agent can currently coordinate this
without writing all the orchestration logic inline.

**What would help:** A `parallel_cd_trajectories(f, deltas, n_seeds, time_budget)` helper
that runs multiple seeded CD trajectories and returns the best result. All agents would
immediately benefit.

---

### 2c. No Convergence Criterion in Pipeline

The system recommendations have proposed a convergence config for gen 10 (Priority 10)
but it has not been implemented. The improvement curve (gen 8-10: -4.1e-10, -2.6e-10,
-1.1e-10) is decelerating by roughly 2x per generation. Without a criterion, the pipeline
will continue indefinitely at sub-noise-floor effort.

The Architect this generation explicitly asked: "Should we declare convergence after gen 10?"
This is a decision that requires a defined criterion.

## 4. Resource Issues

### 4a. LP Overhead at 4.5ms/Trial — INFORMATIONAL

explore_1 spent 340s (out of 496s) on LP trials (68k trials at 4.5ms each) that
returned zero improvements. The null result was valuable — it definitively debunked
idea_023. But the total LP compute spent across gens 8-10 on approaches that eventually
returned null (LP refinement, multi-element perturbation, minimax LP) represents a
significant fraction of total session time.

This is not waste in retrospect — systematic elimination is necessary. But the pattern
should inform gen 11: the remaining search space for multi-element approaches is extremely
narrow and further LP trials are unlikely to yield results.

---

### 4b. Incremental Drift Corrupts CD Results — MODERATE

exploit_1 measured that incremental updates accumulate ~1.4e-12 drift per round.
After 5 rounds, drift is 3.5x the real improvement. Agents in prior generations
(gens 5-9) used incremental CD without FFT resync and their reported improvements
may have been partially phantom.

**Impact:** The gen 10 best scores are verified (FFT resync was used), but the
precision of earlier improvements is uncertain. exploit_1's first run (no resync)
showed incremental C = 1.50286286809259 vs FFT-verified C = 1.50286286819757 —
a 1.05e-10 phantom improvement. This suggests some gen 8-9 intermediate results
may have been more optimistic than reality.

## 5. Knowledge Quality Issues

### 5a. Pattern_012 vs Pattern_023 Contradiction — MODERATE

Pattern_012 says CD improvements decay exponentially. Pattern_023 (new this generation)
says improvement COUNT at 1e-13 is stable at ~5000/round with no decay. Both are true
for different metrics (real C improvement vs improvement count). The gen 10 evaluator
identified this and the agent_gaps report flagged it.

Without annotation, future agents will read both patterns and draw contradictory
conclusions about whether CD is converging.

**Fix:** Add cross-reference annotation to pattern_012: "This refers to real C improvement
per round (which does decay due to incremental drift). Improvement COUNT at ultra-fine
deltas does NOT decay — see pattern_023."

## 6. Experiment Gaps

### 6a. Per-Round FFT Resync CD — HIGHEST PRIORITY UNTESTED

exploit_1 proposed and measured the drift problem but ran resync only every 5 rounds.
No agent in gen 10 ran CD with per-round FFT resync. This is the single highest-priority
improvement to the CD algorithm: it eliminates the drift that currently causes the
incremental tracker to "hallucinate" 3.5x the real improvement.

With per-round resync, agents would have accurate acceptance decisions and true C values
at each round, potentially finding more real improvements in the same time budget.

---

### 6b. Adaptive Delta Range

99.6% of improvements in exploit_1's run were at 1e-13. Deltas from 1e-1 to 1e-9
contributed zero improvements. Using `np.geomspace(1e-14, 1e-11, 30)` instead of
the full 200-value grid would give 5x more rounds in the same time budget, potentially
finding more total improvement.

---

### 6c. Non-Integral-Preserving Multi-Element Moves

All multi-element approaches tested (triplets, quadruplets, minimax LP) required
integral preservation (d_sum = 0). CD works by changing the integral (non-integral-preserving).
The region of non-integral-preserving multi-element moves with k=2-3 has never been tested.
Three independent agents (explore_1, explore_2, evaluator) proposed this experiment.

---

### 6d. Seeded Multi-Trajectory Competition

exploit_1's baked solution (different random trajectory) outperformed its dynamic run.
Five independent 100s trajectories followed by the best → 400s more would exploit this
variance. No infrastructure currently supports this, but it's conceptually straightforward.
