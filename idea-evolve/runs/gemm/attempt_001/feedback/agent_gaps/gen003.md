# Agent Gaps — Generation 3

## Knowledge Gaps

### 1. Assembly Inspection Never Performed
Every gen003 agent independently identified "lack of assembly output" as a top information
gap. No agent has ever inspected the compiled assembly of the best solution. This would
definitively answer:
- Does the compiler keep pre-broadcast A values in zmm registers across the j-loop?
- Is there register spilling in the 8-row kernel?
- What is the actual instruction schedule and port pressure?
- Are there missed optimization opportunities?

**Recommendation:** The experimentator should compile with `-S -fverbose-asm` and analyze
the inner loop. This is the highest-value pure-research task available.

### 2. C Alignment Per Benchmark Size Unknown
Multiple agents discovered alignment constraints empirically (via crashes and failures).
The exact alignment for each benchmark size is still not definitively measured. Explore_1
claims "large C is page-aligned (mmap)" but this is inferred, not measured.

**Recommendation:** A simple fprintf(stderr, "C=%p mod64=%zu", C, (uintptr_t)C%64) in
gemmCandidate would resolve this instantly.

### 3. Mixed Read+Write DRAM Bandwidth Unmeasured
Fact_007 measures pure read and pure write bandwidth separately. The actual kernel performs
simultaneous B reads and C writes. Mixed R+W bandwidth is typically less than either alone.
Experimentator_1 noted this gap after the memcpy experiments.

### 4. cgexec Cgroup Configuration Unverified
Research_1 proposed multi-threading (idea_020) based on the assumption that cgexec allows
2 cores. Whether this is a cpuset (fixed cores 0+1) or a cpu bandwidth limit is unknown.

## Agent Performance Issues

### 5. Exploit_1 Had 12 of 13 Solutions Unscored
Only sol02 had a `.score` file in the population directory. The other 12 solutions either
failed evaluation or had their scores lost. The agent report lists scores for many of them
(e.g., sol03: 152 µs, sol11: 181 µs), suggesting the solutions were evaluated but .score
files were not preserved. This means potentially useful solutions (sol03 at 152 µs, sol11
at 181 µs) were not captured in the population rankings.

### 6. Experimentator Solutions Not in Population Directory
Experimentator_1's solutions (sol01, sol01b, sol02) appear in the experiment directory but
only sol01/sol01b/sol02 have .score files there. They are not in `population/gen003/` for
ranking purposes. The experimentator pipeline routes outputs to `knowledge/experiments/`
rather than `population/`, so experimentator solutions may be systematically excluded from
rankings.

### 7. Research_1 Produced No Code
The research session was thorough but produced zero solutions. The most impactful finding
(SSE 128-bit NT stores as alignment fix) was never implemented. Research agents should be
given enough time or turns to implement at least one proof-of-concept solution.

### 8. Benchmark Variance of 30-40%
Explore_1 reported the same solution measuring 168 µs on one run and 275 µs on another.
This makes <30% differences unreliable for A/B testing. The evaluation infrastructure may
need more repetitions or better isolation to reduce variance.

## Contradictions Between Agents

### 9. Conflicting NT Store Assessments
- Exploit_1: "NT stores don't help sequential writes" (sol02 improvement is compiler layout)
- Research_1: "SSE 128-bit NT stores should give large: 3841→1350 µs" (theoretical)
- Experimentator_1: "The 2.3x standalone result is real but unusable with memcpy"

These aren't truly contradictory — they describe different scenarios. But the knowledge base
should clearly distinguish: (a) 512-bit NT stores are blocked by alignment, (b) aligned-buffer
workaround is net-negative, (c) 128-bit NT stores are a viable untested path.

### 10. 8-Row Kernel: Beneficial or Harmful?
- Exploit_1: "8-row kernel kills C write locality" — sol04/sol05 both regressed
- Explore_1: "8-row gives 16% improvement on large" — sol02 at 168 µs
- Explore_2: "4-row benefit is real — 1.55-1.67x on medium/large"

Resolution: the difference is in implementation. Exploit_1's 8-row used all acc32 registers
upfront (massive spilling) or deferred flush but still processed all 8 rows per j-block.
Explore_1's 8-row used int8 accumulators properly. The technique works when implemented
correctly with int8, but 4-row may be the better tradeoff.
