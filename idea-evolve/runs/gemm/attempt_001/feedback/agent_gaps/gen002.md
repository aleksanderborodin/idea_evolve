# Agent Gaps — Generation 2

## Gap 1: No Agent Solved the C Alignment Problem

The single highest-leverage optimization (NT stores, 2.3x on large) is blocked
by C alignment. Experimentator_1 discovered the constraint but no agent tried
the workaround: allocate an aligned internal buffer, compute with NT stores,
memcpy the result back. This workaround may or may not be net-positive (memcpy
overhead), but it was never tested.

**Priority: CRITICAL** — This blocks the most impactful optimization.

## Gap 2: 8-Row int8 Kernel Never Built

Research agent provided theoretical analysis. Experimentator confirmed int8
accumulation works. Neither built an actual 8-row int8 kernel. Explore agents
were busy with architectural experiments. Exploit agent tried 6-row int16 but
not 8-row int8.

**Priority: HIGH** — Second most impactful optimization after NT stores.

## Gap 3: No Hardware Counter Profiling

Three agents (exploit_1, explore_2, experimentator_1) noted the need for
`perf stat` hardware counter data. None obtained it (likely blocked by
`perf_event_paranoid` setting). This data would definitively answer whether
large is bandwidth- or compute-bound.

**Priority: MEDIUM** — Would inform strategy but the bandwidth measurements
from experimentator_1 partially answer this.

## Gap 4: Exploit Agent Regressed All Variants

Exploit_1 produced 12 solutions, ALL worse than the gen001 best. This suggests
the exploit brief's starting point (gen001 best BLIS solution) is at a local
optimum. Future exploit agents should start from the row-streaming architecture
(idea_014) or combine ideas from both architectures.

## Gap 5: explore_1 Missing .score Files

All 8 explore_1 solutions were missing .score sidecar files. The agent
apparently evaluated solutions (scores in debrief report) but didn't save
.score files. This required the evaluator to re-run evaluate.py on all 8,
consuming significant time and eval budget. Agent prompts should emphasize
that .score files must be written for each solution.

## Gap 6: Research Agent Time Cut Short

Research_1 was interrupted by a "STOP" instruction and couldn't complete
background web research tasks. The findings.md is valuable but incomplete —
web search results for Tiger Lake bandwidth specs and BNN kernel techniques
were never retrieved.

## Gap 7: vpternlogd Truth Table Inconsistency Still Open

Explore_1 report notes that initial 0xCA/0xAC values were incorrect and 0xD8/0xE4
are correct for their operand order. This matches gen001 knowledge. However, no
agent has done a systematic verification of all possible truth table values to
find the optimal one. This is low priority but could matter at the margin.

## Gap 8: No Scoring Metric Verification

Architect raised the question: is the fitness metric geometric mean or true
median (middle value)? For 3 values, the true median equals the middle sorted
value, which is always the medium benchmark. If so, medium alone determines
the score and large doesn't matter. This changes strategy fundamentally. No
agent verified against the actual evaluation code.

## Recommendations for Gen003

1. **Highest priority:** Build a solution that combines row-streaming (idea_014)
   with an aligned-buffer workaround for NT stores on large.
2. **Second priority:** Build and test the 8-row int8 kernel (idea_016).
3. **Experimentator:** Test aligned-buffer NT store workaround; test 8-row int8
   kernel in isolation.
4. **Exploit:** Start from explore_1/sol01 (row-streaming best), not gen001 BLIS.
5. **Research:** Verify the scoring metric (geomean vs true median) — this is
   strategically critical.
