# Experiment Suggestions — Generation 1

Concrete experiments for gen 2, ordered by expected information gain.

---

## EXP-1: No-packing direct kernel (idea_013)

**What to test**: Implement `gemmCandidate` that reads B directly from its original column-major layout without a packing step. For the small benchmark (k_bytes=2, B = 32×2 = 64 bytes), B fits entirely in L1. For medium/large, B also fits in L2 (max 448 KB). Test two variants:
1. Direct strided access: read B[k][n] directly with stride n
2. One-time transpose: transpose B into a row-major layout once (outside the tiling loop), then read contiguously

**Hypothesis**: For the small benchmark specifically, eliminating pack_B could recover the ~5-10 µs still spent on packing. For large, the strided access pattern may cause TLB pressure, making variant 2 (one-time transpose) preferable.

**Expected information gain**: Determines whether packing is strictly necessary given that B fits in cache. If variant 1 is competitive, we learn the CPU prefetcher handles strided B access well. If variant 2 wins, we learn one-time transposition is cheaper than per-panel packing.

**Success criterion**: Any variant scores < 148.18 µs (current best) on at least one benchmark size.

## EXP-2: perf stat hardware counter analysis of NC=256 vs NC=512

**What to test**: Take the best current solution (explore_1/sol10 or equivalent). Build two variants: one with NC=256, one with NC=512. Run both with:
```
perf stat -e L1-dcache-load-misses,dTLB-load-misses,LLC-load-misses,cycles,instructions,cache-references -r 5 <benchmark>
```
on all three sizes. Compare counter deltas between NC=256 and NC=512.

**Hypothesis**: NC=512 causes either (a) L1/L2 conflict misses because the A panel + B panel + accumulator registers exceed some cache set associativity limit, or (b) dTLB pressure because NC=512 × 4 bytes = 2 KB B panel requires more TLB entries than NC=256 (1 KB B panel). Counter data will distinguish these.

**Expected information gain**: High. Resolves a persistent open question across 4+ agent reports. Understanding the root cause enables principled NC selection for all future kernels and problem sizes.

**Success criterion**: Identifying which hardware counter differentiates NC=256 from NC=512.

## EXP-3: int8 accumulation micro-kernel

**What to test**: Modify the best current kernel to accumulate in int8 instead of int16. The inner loop uses `_mm512_adds_epi8` (saturating add for safety) or `_mm512_add_epi8` (with verified no-overflow condition k_bytes ≤ 7 → max diff ±56 < int8 max ±127). Widen to int32 once after the k-loop.

**Variant A**: 4-row kernel with int8 accum (should free 4 zmm registers vs int16)
**Variant B**: 6-row kernel with int8 accum (previously infeasible due to register pressure)
**Variant C**: 8-row kernel with int8 accum (revisit explore_1/sol03 regression with reduced register pressure)

**Hypothesis**: The 8-row kernel in gen 1 (sol03) failed due to register pressure (16 zmm accumulators + temporaries). With int8 (8 zmm accumulators + same temporaries), register pressure is halved. A wider kernel provides better instruction-level parallelism on the micro-kernel hot loop.

**Expected information gain**: Determines whether register pressure was the true bottleneck for wider kernels, and whether int8 accumulation is safe and profitable.

**Success criterion**: Any variant scores < 148.18 µs.

## EXP-4: Assembly inspection of explore_1/sol10

**What to test**: Compile the best solution (sol10) with `-S -O3 -march=native -fverbose-asm` and examine the generated assembly for the micro-kernel inner loop. Look specifically for:
1. Register spills (stack references in the hot loop)
2. Instruction scheduling (are vmovdqu64 loads paired with vpternlogd computations for OOO overlap?)
3. Loop overhead (induction variable increments, branch instructions)
4. Whether the compiler vectorizes the k-loop or leaves it scalar

**Hypothesis**: The compiler is leaving performance on the table through suboptimal register assignment or failing to interleave load and compute instructions. Manual inspection will reveal 1-2 targeted intrinsic changes.

**Expected information gain**: Identifies specific compiler failures. Even if no actionable change is found, confirms the compiler is doing its job well, which is useful context.

**Success criterion**: Finding at least one specific, addressable compiler inefficiency in the hot loop.

## EXP-5: NC sweep — NC=64, 128, 192, 256 for all three sizes

**What to test**: Take the best current solution and parameterize NC. Run benchmarks with NC ∈ {64, 128, 192, 256} (and NC=512 as a reference). Report per-size scores separately for each NC value.

**Hypothesis**: NC=256 may not be optimal for all sizes. The small benchmark (32 rows) with NC=256 means 32/256 = 0.125 — only 13% of the A block is utilized per B panel pass. NC=64 might be better for small, while NC=256 remains optimal for large.

**Expected information gain**: A full NC tuning curve. Identifies whether a single NC works well across all sizes or whether size-specific NC selection would help.

**Success criterion**: Any NC < 256 outperforms NC=256 on the geomean score.

## EXP-6: vpternlogd truth table canonical verification

**What to test**: Write a standalone C++ test (not a GEMM, just a correctness check) that:
1. Generates random 512-bit vectors
2. Computes the boolean formula scalar: `(a_pos | b) & (a_neg | ~b)` and `(a_pos | ~b) & (a_neg | b)`
3. Runs both `vpternlogd(a_pos, a_neg, b, 0xD8)` (explore_1 convention) and `vpternlogd(a_pos, a_neg, b, 0xCA)` (research_1 convention)
4. Reports which convention matches which formula

**Hypothesis**: Both conventions are correct but have different operand orderings. The test will establish the canonical form for all future agents.

**Expected information gain**: Resolves a known discrepancy, creates a reference that can be embedded in the knowledge base. Prevents future silent correctness bugs.

**Success criterion**: A definitive mapping between operand order and imm8 value, documented in idea_011.

## EXP-7: Per-phase timing instrumentation

**What to test**: Add `rdtsc`-based timing around pack_A, pack_B, micro-kernel, and store phases in the best current solution. Run on all three benchmark sizes and report nanoseconds per phase.

**Hypothesis**: For small sizes, pack overhead may dominate. For large, the micro-kernel may still have significant headroom. Per-phase data will show where the remaining ~148 µs goes.

**Expected information gain**: High priority for directing gen 3+ optimization strategy. Once we know which phase is the bottleneck, we can stop spending effort on already-optimized phases.

**Success criterion**: A table of time splits for small/medium/large that can be added to knowledge/facts/.

## EXP-8: Baseline score re-measurement

**What to test**: Run `python3 evaluate.py problem/initial_programs/optimize.py` directly and record the measured geomean time. Compare against the stated 770 µs baseline.

**Hypothesis**: The 770 µs figure may be stale or measured under different system conditions. Given that naive AVX-512 conversions already beat it at 600+ µs, the true baseline may be lower.

**Expected information gain**: Correct framing for all speedup metrics and the 477 µs target. If the baseline is actually lower, the remaining optimization headroom is different from what we think.

**Success criterion**: A confirmed baseline measurement with timestamp, recorded in metrics.yaml and state_of_affairs.md.
