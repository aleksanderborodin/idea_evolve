# Experiment Suggestions — Generation 3

Concrete experiments for the Experimentator and solution agents. Ordered by expected information gain.

## EXP-1 [CRITICAL] Definitive C Alignment Measurement

**What:** Write a diagnostic solution that adds alignment reporting to gemmCandidate:
```cpp
fprintf(stderr, "C=%p mod64=%zu n=%d m=%d\n", (uintptr_t)C, (uintptr_t)C%64, n, m);
```
Run via `python3 evaluate.py diagnostic_sol.py` and capture stderr. Report alignment modulo 64 for all 4 test sizes (correctness + 3 benchmarks).

**What we expect to learn:** Whether C is 16-byte aligned (heap malloc) or 64-byte aligned (mmap for large). If large C is 64-byte aligned, direct `_mm512_stream_si512` NT stores are usable without any workaround, which would be a 2.3x improvement on large. If it's not, SSE 128-bit NT stores (16-byte aligned) are the path.

**Hypothesis:** Large C is 64-byte aligned (mmap returns page-aligned addresses). Medium C is 16-byte aligned. Small/correctness is 16-byte aligned.

**Cost:** 1 solution, ~30 seconds. Resolves all alignment questions permanently.

## EXP-2 [HIGH] 4-Row ternlogd+vpopcntb Kernel

**What:** Take `population/best.py` (141.0 µs, row-streaming kernel). Modify to process 4 output rows simultaneously per B-panel pass. Keep the same ternlogd+vpopcntb compute path; the only change is loading B once and computing 4 rows before advancing j.

Implementation sketch:
```cpp
// Process 4 rows per B-panel load
for (int r = 0; r < n; r += 4) {
    for (int j = 0; j < m; j += NC) {
        // Load B[j..j+NC] into zmm registers (once, shared across 4 rows)
        // For each k_byte:
        //   Broadcast A[r][t], A[r+1][t], A[r+2][t], A[r+3][t]
        //   Apply ternlogd+popcntb for each row independently
        //   Accumulate 4 separate int8 acc vectors
        // At end of j-loop: widen all 4 accumulators to int32, store to C[r..r+3]
    }
}
```

**Hypothesis:** 4x B-load amortization gives 1.55-1.67x improvement on medium/large (validated by explore_2/sol04 with vpshufb kernel — same amortization benefit applies to any kernel). Expected: large ~2300 µs → ~1370-1480 µs, geomean ~80-95 µs.

**What we expect to learn:** Whether B-load amortization transfers from the vpshufb context (where it was measured) to the ternlogd context (where it hasn't been tested). If the ternlogd kernel is more register-pressure-constrained than vpshufb, 4-row may not be feasible and 2-row should be tried instead.

**Expected fitness:** 80-95 µs. Worth ~1.5-1.75x over current best.

## EXP-3 [HIGH] SSE 128-bit NT Stores, Size-Adaptive

**What:** Take `population/best.py` (141.0 µs). Add size-conditional NT store path using `_mm_stream_si128` for large benchmark only:

```cpp
if (n * m * 4 > 8 * 1024 * 1024) {
    // Large: decompose zmm → 4 xmm NT stores (16-byte aligned, safe for heap-allocated C)
    _mm_stream_si128((__m128i*)(C + dst_off + 0),  _mm512_extracti64x2_epi64(acc, 0));
    _mm_stream_si128((__m128i*)(C + dst_off + 4),  _mm512_extracti64x2_epi64(acc, 1));
    _mm_stream_si128((__m128i*)(C + dst_off + 8),  _mm512_extracti64x2_epi64(acc, 2));
    _mm_stream_si128((__m128i*)(C + dst_off + 12), _mm512_extracti64x2_epi64(acc, 3));
} else {
    _mm512_storeu_si512(C + dst_off, acc);  // Regular store for small/medium
}
_mm_sfence();  // After j-loop, not per-store
```

Note: Do NOT use `_mm512_stream_si512` (requires 64-byte alignment). Use `_mm_stream_si128` (requires only 16-byte alignment — always satisfied by heap malloc).

**Hypothesis:** NT stores eliminate cache pollution for 32 MB output, reducing write bandwidth from RFO (read-for-ownership) pattern to streaming. Expected large improvement: 3841 µs → ~1350-1700 µs. Expected geomean: ~95-110 µs.

**What we expect to learn:** Whether the row-streaming kernel's sequential C writes are cache-friendly enough that the hardware prefetcher handles RFO efficiently (making NT stores useless) — OR whether NT stores provide benefit even on sequential patterns due to cache eviction pressure from 32 MB output. If NT stores don't help sequential patterns, large benchmark improvement must come from B-amortization (4-row).

**Prerequisite:** Run EXP-1 first to confirm alignment. If large C IS 64-byte aligned, try `_mm512_stream_si512` instead (fewer stores, no decomposition needed).

## EXP-4 [HIGH] Combined: 4-Row Kernel + SSE NT Stores

**What:** Implement EXP-2 and EXP-3 together in one solution. If EXP-2 produces a working 4-row kernel, add the size-adaptive NT stores from EXP-3.

**Hypothesis:** Effects are multiplicative: 1.67x from 4-row B-amortization × 2.3x from NT stores on large → large drops from 3841 µs to ~1000-1400 µs. Geomean: ~55-75 µs. This would approach or exceed the 60-70 µs realistic target.

**What we expect to learn:** Whether B-amortization and NT stores interact positively (additive benefits) or negatively (e.g., 4-row kernel increases register pressure, causing NT store decomposition to spill registers).

## EXP-5 [HIGH] Assembly Inspection of Current Best Solution

**What:** Compile `population/best.py`'s C++ string with `-S -fverbose-asm -O3 -march=native` and inspect the inner k-loop assembly. Specifically look for:
1. Register spills (`.LBB` spill slots, `vmovdqu [rsp+...]` stores in the loop)
2. Broadcast instruction count vs ternlogd count — confirms vpbroadcastb dominates
3. Whether the compiler auto-unrolls the k-byte loop
4. Port pressure estimate from instruction counts

**What we expect to learn:** (a) Whether the compiler is already making optimal code, or whether there's register allocation waste. (b) Confirmation that vpbroadcastb (2 ops/iter at 1c each) is the timing bottleneck, not vpopcntb (2 ops at 0.5c each). (c) Identify any obvious compiler failures (excessive spills, missing vectorization) that a manual hint could fix.

**Expected outcome:** Either "compiler is optimal, focus on algorithmic changes" or "compiler is spilling X registers, fixing with __attribute__((optimize)) or reordering saves Y%."

## EXP-6 [MEDIUM] cgroup Thread Verification + Multi-Threaded Kernel

**What:**
Step 1 (verification): Write a C++ snippet that creates one pthread and has it return a result. Compile and run inside the cgexec environment (by evaluating a solution that uses pthreads). If it runs without error, multi-threading is safe.

Step 2 (if verification passes): Implement a 2-thread gemmCandidate:
```cpp
// Thread 0: rows 0..n/2-1
// Thread 1: rows n/2..n-1
// Each thread uses NT stores for its slice
// Main thread: _mm_sfence() after pthread_join()
```
Use a static thread pool (pre-created, signaled per invocation) to avoid pthread_create overhead per call.

**Hypothesis:** 2 cores can independently stream to 2 DRAM channels, doubling effective write bandwidth. Large benchmark: 3841 µs → ~2000-2700 µs (1.4-1.9x improvement). Combined with EXP-2+3: geomean ~40-55 µs.

**What we expect to learn:** Whether pthreads are usable within the cgexec cgroup, and whether the Tiger Lake memory controller provides higher bandwidth with concurrent write streams from 2 cores.

**Risk:** If cgexec pins to a single CPU (not just a single core), pthread may fail or serialize. Verification step is mandatory before full implementation.

## EXP-7 [MEDIUM] vpbroadcastb Elimination / Pre-Broadcast Strategy

**What:** Confirmed new finding from experimentator_1: vpbroadcastb is the port-5 bottleneck (1c throughput × 2 broadcasts per k-iter = 2c port-5 per iteration). vpternlogq runs on ports 0/5 (0.5c); vpopcntb on ports 0/1 (0.5c). The inner loop is limited to 1 iteration/cycle by the 2 vpbroadcastb ops.

Current loop pattern per k-byte:
```
vpbroadcastb zmm_a0, [A_row0 + t]   // port 5, 1c
vpbroadcastb zmm_a1, [A_row0 + t+1] // port 5, 1c (if applicable)
vpternlogq ...                       // port 0/5
vpopcntb ...                         // port 0/1
```

Experiment: Pre-broadcast all k_bytes of row 0 outside the j-loop (into k_bytes × zmm registers). For k_bytes=7, this is 7-14 zmm registers. Keeps broadcasts out of the hot path entirely.

**Hypothesis:** Eliminating port-5 pressure from broadcasts in the inner loop reduces iteration time from ~2c to ~1c, a 2x speedup on the compute portion. Impact depends on what fraction of time is compute vs memory-bound.

**What we expect to learn:** Whether the kernel is compute-bound (vpbroadcastb throughput-limited) or memory-bound (DRAM bandwidth for C writes). If compute-bound: pre-broadcasting gives ~2x. If memory-bound: no benefit. Combined with EXP-5 (assembly inspection), this resolves the compute-vs-memory debate definitively.

## EXP-8 [LOW] Benchmark Variance Study

**What:** Run the current best solution 50 times via a custom evaluation harness and record the distribution of scores. Report mean, std, P5, P50, P95 for each benchmark size.

**What we expect to learn:** The minimum meaningful improvement threshold. If variance is ±15%, then only improvements >15% are statistically reliable. Currently, the reported 4.3% gen002→gen003 improvement (147.26 → 141.0 µs) is likely within noise. This would establish whether sol02's improvement is real or an artifact of measurement noise.

**Why this matters for the pipeline:** If variance is high, agents should be briefed to target improvements >30% rather than incremental refinements. Small improvements (< noise floor) waste evaluation time.

## EXP-9 [LOW] User Intervention: Harness Modification to Aligned C

**What:** Request user approval to modify `fast-conv/bench_harness.cpp` to allocate C with `_mm_malloc(n * m * 4, 64)` instead of `std::vector<int>`. This requires updating the deallocation too (`_mm_free`).

**What we expect to learn:** With 64-byte aligned C, direct `_mm512_stream_si512` NT stores work without decomposition or workarounds. Expected large improvement: 3841 → ~1300-1700 µs (2-3x). This would be the highest single-change improvement possible.

**Why flagged as user intervention:** The harness is described as read-only for agents (CLAUDE.md). But modifying it would unlock NT stores permanently for all future agents. User should decide if this is in scope.
