## EXP-1 [CRITICAL] Verify Scoring Metric — Read evaluate.py

**What:** Read `problem/evaluate.py` and `problem/validate.py`. Find where the three
benchmark scores (small, medium, large) are combined into a single fitness value.
Confirm whether it is:
- (a) `(s * m * l) ** (1/3)` — geometric mean
- (b) `sorted([s, m, l])[1]` — true median (= always the medium value for 3 sizes)

**Who should do it:** Any agent in gen 3 (or the user before gen 3 launches). This is
a read-only task, takes <5 turns.

**Hypothesis:** The function uses `(s * m * l) ** (1/3)` based on common practice for
multi-benchmark summaries. If it uses true median, the entire large-benchmark optimization
strategy must be abandoned and effort concentrated on medium.

**What you'll learn:** Whether the entire gen-2 strategy (optimize large with NT stores)
is valid or wasted.

## EXP-2 [CRITICAL] Aligned-Buffer NT Store Workaround

**What:** Take `population/gen002/explore_1/sol01.py` (row-streaming, 147.26 µs). Modify
the C++ kernel to:
1. Allocate `alignas(64) int* cbuf = (int*)std::aligned_alloc(64, n * m * sizeof(int))`
2. Compute gemmCandidate into cbuf using `_mm512_stream_si512`
3. Call `_mm_sfence()`
4. `std::memcpy(C, cbuf, n * m * sizeof(int))`
5. `free(cbuf)`

Apply this only when `(size_t)n * m * 4 > 8*1024*1024` (large benchmark, not small/medium).

**Expected results:**
- Large benchmark: ~4000 µs → ~2000-2500 µs (NT store 2.3x benefit vs ~15 GB/s memcpy overhead)
- Medium benchmark: unchanged (~228 µs, below bandwidth floor — don't use NT stores)
- Small benchmark: unchanged (~3-4 µs, compute-bound)
- Geomean: ~147 µs → ~80-110 µs

**Hypothesis:** The NT store benefit (2.3x on 33 MB output, measured by experimentator_1)
should survive the memcpy overhead because: (a) memcpy is faster than writing back dirty cache
lines, (b) the intermediate buffer is used once (streaming pattern). The evaluator's back-of-
envelope calculation (Experiment 1 notes) shows a net win of ~3467 µs on large.

**Fallback if memcpy erases the gain:** Try mmap + MAP_POPULATE for the buffer, or test
only on systems where C is guaranteed aligned (check harness).

## EXP-3 [HIGH] 8-Row int8 Micro-Kernel (Standalone)

**What:** Implement a clean 8-row int8 kernel as a standalone test, separate from the
full solution. Starting from the 4-row int16 kernel:
1. Change accumulator width: `__m512i acc[8]` (int8) instead of `__m512i acc[4][2]` (int16)
2. Process 8 A rows per k-loop iteration (pack 8 rows instead of 4)
3. Flush int8 → int32 every 15 k-iterations (overflow safety: max ±120)
4. Benchmark all 3 sizes

**Expected results:** Based on experimentator_1 data:
- int8 improvement: 11-13% on kernel+store time
- 8-row: may reduce B loads per C-output by 2x (amortize over 8 rows instead of 4)
- Combined: potentially 20-30% on medium and large

**Hypothesis:** int8 accumulators halve port-5 pressure by eliminating vpmovsxbw widening in
the hot loop (experimentator_1, Exp 2b). 8 rows doubles compute density per B-panel load.
Both effects compound.

**Validation concern:** k_bytes=32 (correctness test) overflows int8. Must flush every 15
iterations even for correctness tests (k_bytes ≤ 15 is safe for benchmarks but tests use
k_bytes=32). The experimentator validated int8 only for k_bytes ≤ 7.

## EXP-4 [HIGH] Combine EXP-2 + EXP-3 (Full Stack)

**What:** After EXP-2 and EXP-3 succeed independently, combine:
- Row-streaming architecture (explore_1/sol01 base)
- 8-row int8 kernel (EXP-3)
- Aligned-buffer NT stores for large (EXP-2)
- Adaptive NC: NC=128 for medium, NC=m (no tiling) for large (experimentator_1 NC sweep)

**Expected results:**
- Large: ~4000 µs → ~1500-2000 µs (NT stores + 8-row B-load amortization)
- Medium: ~228 µs → ~180-200 µs (int8 + adaptive NC=128)
- Small: ~3.5 µs → ~2-3 µs (int8, no-pack for small k_bytes=2)
- Geomean: ~147 µs → ~40-70 µs

**Hypothesis:** These three optimizations are largely orthogonal (stores, kernel width,
accumulator type) and should compound. Geomean target of 60 µs (physics-limited) is achievable
with all three in place.

## EXP-5 [MEDIUM] vpshufb Nibble-LUT Kernel (Alternative Compute Path)

**What:** Replace ternarylogic+popcnt compute with precomputed 16-entry nibble LUTs:
1. Precompute for each A-byte the 16 possible popcount sums for each nibble of B
2. Use `_mm512_shuffle_epi8` (vpshufb) to look up and sum nibble contributions
3. One vpshufb per nibble × k_bytes nibbles = 2×k_bytes vpshufb instructions per row

**Expected information gain:** vpshufb uses port 0/1 (not port 5), completely eliminating
the port-5 bottleneck identified by experimentator_1. This could allow 2x throughput if
port 5 is truly the bottleneck.

**Hypothesis:** Port 5 bottleneck (20-28 uops/k-iter on port 5) limits throughput. vpshufb
shifts compute to port 0/1 and could relieve the bottleneck. However, LUT overhead (16 entries
× k_bytes lookups) may offset this. First result will tell us whether port 5 is actually the
binding constraint.

**If it fails:** We'll know port 5 is not the bottleneck and can eliminate this class of
optimization from the search space.

## EXP-6 [MEDIUM] Verify fact_004 Instruction Port Assignments

**What:** Read `fast-conv/gemm/` reference implementations. Check the assembly output
of the best current solution (`objdump -d population/gen002/explore_1/sol01.py` after
compiling) and cross-reference with uops.info for Tiger Lake (ICL microarchitecture).
Specifically verify:
- vpopcntb: is it port 0/1 (as experimentator_1 observed) or port 5 (as fact_004 claims)?
- vpbroadcastb: port 5 only or also port 0?
- vpternlogq: port 0/5 (both sources agree)

**Expected information gain:** Definitively resolves the 2-generation dispute. If vpopcntb
is port 0/1 (not port 5), the throughput model is different and some bottleneck analysis
needs revision. Specifically: if vpbroadcastb (port 5 only) and not vpopcntb is the binding
constraint, the 8-row kernel optimization path changes.

## EXP-7 [MEDIUM] Per-Size Adaptive Pack Strategy

**What:** Modify the best solution to detect benchmark size at runtime and use:
- Small (k_bytes=2): skip pack_A entirely; broadcast A bytes inline (explore_1's technique
  already does this partially). Skip pack_B and use direct B access (B=2KB, fits in L1).
- Medium (k_bytes=4): keep BLIS packing, use NC=128 (experimentator_1 result)
- Large (k_bytes=7): keep pack_B (B=458 KB, fits in L2), no NC tiling, NT stores

**Expected results:** Small benchmark ~4 µs → ~1-2 µs (eliminate packing overhead, B fits in L1)

**Hypothesis:** research_1 identified pack_A scalar overhead as ~55% of small benchmark time.
For small, both B (2KB) and A (128×2=256 bytes) fit in L1. Eliminating packing could give
3-5x improvement on small. Geomean impact depends on scoring metric (see EXP-1).
