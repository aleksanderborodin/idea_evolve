# System Analysis — Generation 3

## Executive Summary

Gen003 made a marginal score improvement (147.26 → 141.0 µs, 4.3%) while producing high-value negative knowledge. The generation succeeded intellectually but failed operationally in two areas: missing `.score` files for 12 of exploit_1's 13 solutions, and a State of Affairs that is two generations stale. The pipeline is approaching a knowledge consolidation crisis — key findings from gen002-003 are not reflected in the top-level strategic document that all agents read first.

---

## 1. Pipeline Problems

### [CRITICAL] State of Affairs Is Two Generations Stale

**Evidence:** `knowledge/state_of_affairs.md` still has `generation: 1, best_score: 148.18`. It was written after gen001. The gen002 consistency review was launched but produced zero output files in 31.9s (noted in architect.md: "Gen-2 consistency review completely failed"). Gen003 is the every-3rd-gen trigger, so a consistency review should run this generation.

**Impact:** All gen003 agents started from a strategic document that listed dead ends as unexplored, wrong best scores, and missing architecture-level insights (row-streaming as established best, memory bandwidth wall). Each agent had to reconstruct context from the clusters and facts files. This costs 10-20 turns per agent that should have been spent on experiments.

**Root cause:** The gen002 consistency review ran with a 31.9s timeout — far too short. The orchestrator likely used a very low default or the session crashed immediately. This should be investigated.

---

### [CRITICAL] 12 of 13 exploit_1 Solutions Have No .score File

**Evidence:** The evaluator report explicitly states: "Exploit_1 had only 1 of 13 solutions scored in population directory (sol02 at 141.0 µs)." The exploit_1 debrief lists scores for sol01 (513µs), sol03 (152µs), sol04 (399µs), sol05 (340µs), etc. — but these exist only in the report text, not as `.score` files.

**Impact:** (1) Rankings miss potentially useful solutions (sol03 at 152µs would be rank 2). (2) The evaluator had to work from report-text scores rather than validated JSON sidecars. (3) eval cache may have these results, but they can't be recovered without content hash matching.

**Root cause:** One of: (a) agent wrote scores to workspace output but orchestrator routing didn't copy `.score` files alongside `.py` files; (b) agent used evaluate.py correctly but the `.score` file was written to a different path; (c) the agent evaluated in-place and the scores were in workspace but workspace was cleaned. REC-5 from gen002 (auto-write `.score` in evaluate.py) remains unimplemented. This is the direct cause.

**Severity:** Critical. Recurring from gen002 (explore_1 had same issue).

### [MODERATE] Research_1 Allocated as Pure Research, Produced No Code

**Evidence:** research_1 report: "Pure research session; no code written." The agent's conclusion was that `row-streaming + size-adaptive 128-bit NT stores` is the single highest-leverage change — but ran out of time before implementing it. This is the #1 unexplored experiment.

**Impact:** Wasted an agent slot for code production. Research findings from gen002 were already thorough enough to support implementation in gen003. A research agent that doesn't write code is net-negative in a generation where the coverage matrix has obvious unimplemented high-priority combinations.

**Assessment:** Research agents are appropriate in early generations or when the path forward is unclear. By gen003, the path forward was clear (4-row ternlogd+popcnt, SSE NT stores) and implementation was needed, not more analysis.

### [MODERATE] Explore_2 Directed to Dead End with Partial Prior Evidence

**Evidence:** explore_2 was briefed to implement idea_018 (vpshufb LUT kernel). The premise was that vpshufb runs on port 0/1, not port 5. The experimentator's gen002 microbenchmark data actually pointed to vpbroadcastb as port-5 bottleneck, not vpopcntb — but the architect's brief seems to have relied on an unverified hypothesis about vpshufb.

**Outcome:** explore_2's best result was 342µs (2.3x worse than current best). idea_018 is now debunked.

**Value:** Not zero — explore_2 independently validated that 4-row B-load amortization gives 1.55-1.67x on medium/large. This is a critical positive finding. But the primary objective (vpshufb beats ternlogd) failed due to wrong port assignment assumption.

**Root cause:** The gen002 system recommendations did not flag that the vpshufb idea was based on an unverified port assumption. REC-9 said to move fact_004 to disputed but the specific vpshufb→port 0/1 assumption was not called out.

### [MODERATE] Generation Loop Is Slowing — Same Gap for 3 Generations

**Evidence:** gen001: 148.18µs, gen002: 147.26µs (-0.6%), gen003: 141.0µs (-4.3%). The progress rate is decelerating. Three generations of work have produced only 4.9% total improvement. The pipeline has not yet attempted the highest-leverage combinations (4-row ternlogd+popcnt, SSE NT stores) that were identified by gen002.

**Root cause:** Agents are identifying the right experiments but either (a) being briefed to explore other directions first, or (b) running out of time to implement the identified priorities. The knowledge base is correct; the execution is not following through.

## 2. Missing Capabilities

### [MODERATE] No Assembly Inspection Capability

**Evidence:** All four code-producing agents independently called for assembly inspection. exploit_1: "I couldn't verify whether my changes produced better or worse machine code." explore_1: "Never inspected whether the compiler spills registers." explore_2: "Never inspected the generated ASM." experimentator_1: "Should have verified with -fopt-info-inline flags."

**Impact:** Agents are making optimization decisions without seeing the actual compiled output. Multiple failed experiments (8-row kernel, NT stores, column blocking) could have been predicted from assembly analysis. This likely wasted 30-40 evaluation turns across gen003 agents.

**Recommendation:** Add a standard instruction to all solution agent briefs: compile the best solution with `-S -fverbose-asm -O3 -march=native` and inspect the inner loop before writing variants. Or create an `inspect_asm(sol_path)` helper.

---

### [MODERATE] No Verified C Alignment Per Benchmark Size

**Evidence:** Three independent agents (exploit_1, explore_1, research_1) requested a definitive measurement. exploit_1 discovered unalignment by crash (sol12 segfault). explore_1 observed "C IS 64-byte aligned for the large benchmark" (mmap behavior) but couldn't verify medium. The current best NT store strategy depends critically on knowing this.

**Impact:** Agents can't safely implement NT stores without this data. Two generations of NT store experiments have been hampered by alignment uncertainty.

**Fix:** Add `fprintf(stderr, "C align: %zu n=%d m=%d\n", (uintptr_t)C%64, n, m)` to a diagnostic solution and run it. This takes 5 minutes and resolves all alignment questions permanently.

---

### [MINOR] No Benchmark Variance Quantification

**Evidence:** explore_1 observed 30-40% variance between runs of the same solution (168µs vs 275µs for sol02). This means improvements below ~30% are within noise — but agents are reporting improvements of 4.3% as meaningful.

**Impact:** The gen003 best (141.0µs vs 147.26µs, 4.3%) may not be a real improvement. The evaluator correctly flagged: "Sol02's improvement is likely fragile. A 4.3% improvement that may come from a dead code branch changing instruction alignment is not a robust optimization."

**Recommendation:** Run a 50-rep stability test on the claimed best before treating it as the new baseline.

## 4. Knowledge Quality Issues

### [MODERATE] fact_004 Was Wrong — Now Corrected

**Evidence:** experimentator_1 confirmed vpopcntb is port 0/1 (throughput 0.5c), NOT port 5 as fact_004 claimed. vpbroadcastb confirmed as the sole port-5 bottleneck at 1c throughput. The evaluator should have updated/deprecated fact_004.

**Impact if not fixed:** Gen004 agents reading fact_004 will design kernels to eliminate vpopcntb (wrong bottleneck) instead of vpbroadcastb (actual bottleneck).

---

### [MINOR] idea_015 Confidence Recalibration Is Needed

**Evidence:** idea_015 (size-adaptive NT stores) had confidence 0.7. Multiple gen003 agents showed the 2.3x measurement doesn't transfer to integrated kernels: explore_1 found NT stores same-or-worse even when C is aligned for large; experimentator_1's end-to-end tests all regressed. The evaluator said confidence was lowered to 0.4.

**However:** research_1 correctly points out the specific combination `row-streaming + SSE 128-bit NT stores (aligned for large)` has NEVER been tested. The 2.3x standalone measurement used different kernels and different NT store instructions. The evaluator's lowered confidence is premature — the experiment hasn't been done correctly yet.

**Recommendation:** Confidence 0.4 is appropriate for 512-bit zmm NT stores. A separate idea for 128-bit SSE NT stores on the row-streaming kernel (which HAS 16-byte-aligned C for large) should be tracked at confidence 0.8.

## 5. Resource Issues

### [MODERATE] 24µs Target Is Physically Impossible — User Confirmation Needed

**Evidence:** Three agents (exploit_1, research_1, experimentator_1) independently computed the bandwidth floor. Medium benchmark (n=64, m=4096, k=?) at 220µs is already at ~96% of its theoretical minimum (220-230µs). Even with perfect large optimization to its bandwidth floor (~2000µs), geomean ≈ (3.69 × 225 × 2000)^(1/3) ≈ 90µs. The realistic achievable range is 50-80µs.

**This was CRITICAL in gen002 system_recommendations (REC-2) and remains unaddressed.** Two generations have passed without user confirmation of the realistic target.

**Impact:** Agents are computing with reference to an impossible target, which either causes them to declare the problem unsolvable or to search for approaches (compressed output, non-standard formats) that may not be valid solutions.

## 6. Experiment Gaps

### Key untested combinations as of end of gen003:

1. **4-row ternlogd+vpopcntb kernel** (idea_022 + idea_004): explore_2 showed 1.55-1.67x B-amortization benefit with vpshufb kernel; never applied to the actually-good ternlogd kernel. **This is the #1 priority.**

2. **SSE 128-bit NT stores, size-adaptive, on row-streaming kernel**: The specific combination of row-streaming architecture + `_mm_stream_si128` (16-byte aligned, usable for large mmap'd C) has never been tested. Previous NT store experiments used either wrong alignment assumptions or wrong kernel base.

3. **Multi-threading** (idea_020): cgroup contains cores 0+1. Zero attempts across all generations.

4. **Assembly inspection of best solution**: Never done. Should have been done in gen001.

5. **vpbroadcastb elimination from inner loop**: Now confirmed as the port-5 bottleneck at 1c/iter (2 ops × 1c = 2c port-5 per k-iteration). Eliminating or reducing broadcasts could unlock further improvement.

6. **Harness modification for direct NT stores**: If validate.py/bench_harness.cpp allocates C with aligned_alloc(64, ...) instead of std::vector<int>, the 2.3x NT store benefit becomes directly applicable. This requires user intervention but would be the most impactful single change.
