# System Analysis — Generation 1

## Executive Summary

Generation 1 produced an exceptional result: best score 148.18 µs (5.20x over baseline, 3.22x better than the 477 µs target) in a single generation. The pipeline's core workflow — evaluate-immediately, lean prompts, debrief recovery — functioned correctly. One of four agents (explore_2) produced zero solutions due to excessive context-reading before writing code. The knowledge base was bootstrapped well. Three significant systemic issues are identified.

---

## Pipeline Problems

### [CRITICAL] explore_2 produced zero solutions — 25% of agent capacity wasted

**Evidence**: explore_2's debrief states "The session was interrupted before sol01.py was written." The agent spent its entire budget reading 7+ files. Agents were supposed to write first and read more later (per the evaluate-immediately mandate), but explore_2 reversed this order. The agent gap report independently identifies this as "a complete waste of an agent slot."

**Root cause**: The explore agent brief may not enforce a hard "write sol01 within the first N turns" requirement. Reading context feels productive and is easy to do, but delays code output. The explore.md template enforces evaluate-immediately once code exists, but does not cap pre-code reading time.

**Impact**: Direct loss of one agent's exploration output, and potential loss of an entirely different optimization direction (VNNI/8×64 kernel) from the search space in gen 1. The gap was not compensated by the other agents.

### [MODERATE] vpternlogd truth table discrepancy unresolved

**Evidence**: explore_1 uses imm8 values 0xD8/0xE4; research_1 independently derived 0xCA/0xAC. Both produce correct results per evaluation (no correctness failures), meaning operand ordering differs between the two agents. The evaluator notes this but flags it as a potential source of confusion. The agent gaps report (gap 4) identifies it as a risk: "A bug here would produce silently incorrect results."

**Root cause**: No systematic truth-table verification test exists. Research and solution agents independently derive constants without a canonical reference. This is a correctness risk that grows as more agents build on top of these constants.

**Impact**: Currently benign (solutions evaluate correctly), but downstream agents building on either convention may mix operand orders and produce incorrect, hard-to-debug solutions.

### [MODERATE] NC=512 regression root cause unknown

**Evidence**: Every agent that tested NC=512 (explore_1: sol01, sol06; full_1: compared NC settings) observed consistent performance regression vs NC=256. No profiling data exists. The evaluator notes it as an "open question" requiring hardware counters. Two agents listed hypotheses (cache associativity, TLB pressure) but none was tested.

**Root cause**: No profiling infrastructure available to agents. `perf stat` is the correct tool but agents would need explicit guidance in their brief to run it, and the output format needs to be interpretable.

**Impact**: Without understanding the NC=512 regression, the pipeline cannot make informed decisions about NC for larger problem sizes or future kernels. It also cannot rule out that NC=512 is better in some regimes (e.g., very large n).

---

## Missing Capabilities

### [MODERATE] No perf/profiling infrastructure for agents

**Evidence**: Multiple agents (explore_1, full_1, research_1, evaluator) independently identified the same gap: lack of hardware counter data (`perf stat`), assembly output (`-S`), and per-phase timing instrumentation. This gap appeared in 4 out of 5 reports.

**Current state**: Agents infer bottlenecks from score deltas between solutions — an indirect and noisy signal. pack_B was identified as a bottleneck only after a solution that vectorized it showed a large speedup; the actual time fraction was never measured directly.

**Missing**: A helper script or evaluation sidecar that runs `perf stat` on the benchmark and returns structured output. Even a simple "write the solution, then run it with timing instrumentation" workflow would help.

### [MINOR] No assembly inspection workflow

**Evidence**: Evaluator, explore_1, and research_1 all note that compiler output was not inspected. The evaluate.py pipeline compiles C++ internally; agents cannot easily access the generated assembly.

**Missing**: A way for agents to request assembly output (e.g., run `g++ -S -O3 -march=native` on a specific C++ file). This would reveal register spills, missed scheduling, and vectorization failures.

---

## Prompt Problems

### [CRITICAL] explore.md does not enforce a "write first" time budget cap

**Evidence**: explore_2 read 7+ files before writing code. The evaluate-immediately mandate (write one → evaluate → update header) is clearly effective once code exists, but it does not trigger until code is first written. There is no instruction in the brief like "write sol01 within your first 10 turns regardless of how much context you've read."

**Recommendation**: Add explicit instruction to explore.md: "Your FIRST action after reading problem/description.md and problem/initial_programs/optimize.py is to write sol01.py and evaluate it. Do not read more than 2-3 files before producing your first solution. Broader reading comes AFTER your first evaluation."

### [MINOR] Research agent findings not fed back to solution agents in same generation

**Evidence**: research_1 produced 12 findings (Finding 1-12) but solution agents ran concurrently. research_1's findings were available only after solution agents had already completed. The Architect had to predict what research would find when designing solution agent briefs.

**Current limitation**: This is inherent to the parallel execution model (research runs in the same parallel group as solution agents per the gen1 manifest). Some high-value findings (e.g., int8 accumulation safety, KC tiling removal, B-fits-in-L2) were re-discovered empirically by solution agents rather than being used proactively.

**Possible fix**: Move research to a prior sequential group, so findings are available when solution briefs are written. Trade-off: adds latency to each generation.

## Resource Issues

### [MINOR] Only 14 solutions from 4 agent slots (effective 3 productive agents)

**Evidence**: explore_1 produced 10, full_1 produced 4, explore_2 produced 0, research_1 produced research findings (not solutions). With explore_2 fully productive, an additional 5-8 solutions testing different optimization directions (VNNI, 8-row kernel, no-packing) could have been produced.

**Context**: The result is still outstanding. This is not a crisis, but the wasted capacity represents an efficiency loss.

---

## Knowledge Quality Issues

### [MINOR] vpternlogd imm8 convention not canonicalized

**Evidence**: idea_011 records vpternlogd as useful but does not specify which operand convention (0xD8/0xE4 vs 0xCA/0xAC) is canonical. Downstream agents reading idea_011 will not know which to use, or will not know there's ambiguity.

**Fix**: idea_011 should be updated to document both conventions with their operand orders, or a single canonical form should be established by testing.

### [MINOR] "Baseline score of ~770 µs" may be stale

**Evidence**: Both explore_1/sol01 (654 µs) and full_1/sol01 (602 µs) — first AVX-512 attempts — beat the stated baseline immediately, suggesting the 770 µs figure may be higher than the actual measured baseline. The evaluator flagged this.

**Risk**: If the baseline score is wrong, the speedup factor and target (477 µs) are also suspect. Agents may be optimizing toward a target that was calculated from an incorrect baseline.

---

## Experiment Gaps

### [HIGH PRIORITY] int8 accumulation in the micro-kernel

**Evidence**: research_1 independently derived that k_bytes ≤ 7 → max accumulated diff ≤ ±56, which fits in int8 (range ±127). This would halve register pressure (1 zmm accumulator per row vs 2 for int16), potentially enabling wider kernels. explore_1 tried int16 accumulation successfully but int8 was never tested.

### [HIGH PRIORITY] No-packing direct kernel (idea_013)

**Evidence**: The evaluator and multiple agents identified this as the single highest-priority untested idea. B always fits in L2 (max 448 KB); for small benchmarks it fits in L1. Eliminating pack_B overhead could give another step-change improvement for small/medium sizes.

### [MEDIUM PRIORITY] NC sweep below 256

**Evidence**: Only NC=256 and NC=512 were tested. NC=128 and NC=192 may be better for small benchmarks. explore_1 explicitly noted this as a priority experiment.

### [MEDIUM PRIORITY] Per-phase timing instrumentation

**Evidence**: Multiple agents need this to guide optimization priorities. Without knowing the time split between pack_A, pack_B, micro-kernel, and stores, it's impossible to know whether further work on the kernel, the packing, or the memory access pattern will have the biggest payoff.

---

## Overall Assessment

The pipeline is functioning well. The evaluate-immediately workflow is producing measurable results. The debrief system is capturing knowledge. The evaluator produced a high-quality bootstrap knowledge base. The primary systemic issue is explore_2's complete failure to produce solutions, which is directly attributable to a missing "write-first" mandate in the explore prompt. The NC=512 regression mystery and vpternlogd convention discrepancy are moderate issues that should be resolved via targeted experiments in gen 2.
