## Pipeline Problems

### [CRITICAL] Scoring Metric Ambiguity — Strategic Direction Unknown

**Evidence:** Both the Architect (report line 39) and the Evaluator (report section 2) and
the agent_gaps file (Gap 8) flagged this unresolved: is "fitness" computed as geometric mean
`(small × medium × large)^(1/3)` or as the true median (middle sorted value)?

For 3 values, the true median is always the medium benchmark. If fitness = median:
- Large benchmark is irrelevant to score
- Small benchmark is irrelevant to score
- All NT-store optimizations for large (the #1 recommended direction) have zero impact on score
- All effort should be on medium exclusively (~228 µs, near bandwidth floor)

If fitness = geometric mean:
- Large dominates (3176 µs vs 228 µs medium, 4 µs small)
- NT stores for large are the highest-leverage optimization
- Gen 3 strategy is completely different from the median case

**Two full generations and no agent has read `problem/evaluate.py` to check.** This is a 5-minute
task that would resolve a question affecting the entire strategic direction of the pipeline.

**Severity: CRITICAL**

---

### [CRITICAL] 24 µs Target is Below the Measured Bandwidth Floor

**Evidence:** experimentator_1 (Experiment 4) measured actual DRAM write bandwidth:
- Stream writes at 32 MB: 24.84 GB/s
- Regular writes at 32 MB: 11.38 GB/s
- Large output (33.55 MB C) → minimum write time at stream bandwidth: **2054 µs**

Best-case geomean floor: ∛(2 × 120 × 1000) ≈ **62 µs** (optimistic estimates for each size).

The target is 24 µs — a factor of 2.6x below the physics limit. This cannot be achieved
by any algorithm that writes n×m×4 bytes of int32 output to DRAM.

**This needs to be communicated to the user.** Two scenarios:
1. The target was set for different benchmark sizes (e.g., the user intended smaller matrices)
2. The user is aware and expects the pipeline to find a fundamentally different output strategy
   (e.g., compressed output, int8 output, bit-packed output)

exploit_1 also flagged this (report section 3): "Medium (64×16384) minimum write at 30 GB/s
= 133 µs. Target is 4x below physics limit." The research agent confirmed it (Finding 1).

**Severity: CRITICAL** — Without a revised or clarified target, the pipeline will spend
resources chasing an impossible goal.

## Missing Capabilities

### [HIGH] No Automatic .score File Writing

`evaluate.py` currently returns results but agents must manually capture and write `.score`
files. Two consecutive generations have had this problem. A simple change to `evaluate.py`
to always write a sidecar file (named `{solution_path}.score`) without explicit agent action
would eliminate this class of error entirely.

### [MEDIUM] No Scoring Metric Documentation

There is no document explicitly stating how the fitness metric is computed. The problem
description uses "geometric median" but this term is ambiguous. `problem/metrics.yaml`
should have a `metric_description:` field that unambiguously defines the formula.

### [MINOR] No Bandwidth Measurement Helper

Three agents independently requested a bandwidth measurement utility
(explore_2, experimentator_1, research_1). The experimentator ran a manual microbenchmark.
A `helpers/bandwidth_measure.py` script would let any agent instantly get the current
machine's actual bandwidth measurements without re-deriving them.

executed:

   independently by explore_1, explore_2, research_1.

that would resolve the most critical strategic ambiguity in the pipeline.
