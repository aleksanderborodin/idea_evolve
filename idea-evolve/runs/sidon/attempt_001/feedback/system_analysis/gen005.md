# System Analysis — Generation 5

**Date:** Post-gen005 review
**Current best score:** 105 (up from 102 plateau)
**State:** Algebraic ceiling confirmed at 105. Entering pure computational search phase.

---

## Summary

Generation 5 was the most productive since gen 2. The Rokicki-Dogon database delivered a
+3 breakthrough (102→105). However, several pipeline inefficiencies consumed significant
compute: one agent wasted its entire budget on a known-bad algebraic construction, two agents
duplicated the same database download, and CP-SAT received its fifth consecutive run with
inadequate time budget. The strategic direction is now clear and unambiguous — the pipeline
must orient fully toward computational search methods.

---

## Pipeline Problems

### [P1] MODERATE — Duplicate Rokicki-Dogon work between experimentator_1 and research_1

**Evidence:** Both experimentator_1 and research_1 independently downloaded the Rokicki-Dogon
database from cube20.org/golomb/, parsed the same mark lists, and produced identical solutions
(both: sol01=105, sol02=104). The agent_gaps/gen005.md notes this explicitly as gap #1.

The previous system_recommendations (gen 4) identified this as Priority 1 critical action:
"assign dedicated Rokicki-Dogon data-fetch task." The Architect assigned it to both agents
independently rather than routing it clearly to one.

**Root cause:** The brief structure gave both agents overlapping mandates. The Architect's
gen 5 report acknowledges this risk but executed both anyway, presumably as independent
confirmation. While verification has value, having two separate agents spend 1000-1300s each
on the same download-and-parse task is wasteful. One agent should do retrieval; the second
should receive the data and extend it.

**Fix:** When a knowledge gap requires a one-time data fetch (database download, literature
lookup), assign a single agent as the canonical fetcher. Other agents that need the same data
should be given the file path in their brief, not tasked to fetch independently.

---

### [P2] CRITICAL — explore_2 wasted entirely on a known-invalid algebraic construction

**Evidence:** explore_2 implemented `S = {i*p + (i² mod p) : i = 0,...,p-1}` for p=97,
producing 312 violations. The agent's own debrief notes: "The claimed Bose-Chowla construction
is NOT i*p + (i² mod p) for large p." The pipeline has explicitly documented that Ruzsa-type
constructions (φ(x) = x*p + (x²%p)) fail in integers since gen 4 (explore_2/gen4 tested
exactly this). The gen 4 snapshot records: "Ruzsa and CRT Constructions Don't Work in
Integers" and specifically calls out "Ruzsa φ(x)=x*p+(x²%p)."

The agent's brief must have described "Bose-Chowla construction" without providing the
critical context that the only valid Bose-Chowla formulation is Z_{q²+q+1} cyclic — which
is precisely the Singer construction already exhausted.

**Severity:** This entire agent session produced zero valid solutions above baseline and
consumed a full 1200s agent budget.

**Root cause:** The Architect brief was underprescribed. It named an algebraic family without
specifying which formula to use or flagging that the naive formula was already tried (and failed)
in gen 4 under a different name. The State of Affairs listed "Bose-Chowla / Affine Plane"
as a new idea (idea_022, created in gen 5 by the evaluator), which is confusing — this is
the same thing as Singer under a different label.

**Fix:**
1. The brief for any algebraic construction attempt must cite the specific formula, not just the name.
2. When the Architect considers an approach similar to one already tried, the brief must include
   a "Don't do X (tried in genNNN)" note.
3. idea_022 (Bose-Chowla AP) should be marked as "established" and its description should
   explicitly state it is algebraically equivalent to Singer — agents must not attempt
   an independent derivation.

---

### [P3] MODERATE — CP-SAT chronically underpowered; repeated UNKNOWN without learning

**Evidence:** CP-SAT has now run in 4 separate generations (gen 4: 1×600s, gen 5 full_1: 3×600s)
and returned UNKNOWN every single time. Total CP-SAT CPU time across the run: ~2400s on
k=103, all UNKNOWN. No improvement has been extracted.

The gen 5 full_1 report identifies an important nuance: the Singer warm-start may actively
**hurt** the solver. Small-N analysis (q=7, q=11) shows that optimal Sidon sets share almost
no elements with Singer sets (3/8 and 1/12 overlap respectively). The CP-SAT hint is pointing
toward the wrong region of the search space.

**Severity:** Each full_1 session (1800-1900s) costs nearly as much as two explore agents.
Five consecutive UNKNOWN results suggest the solver approach needs restructuring, not more time.

**Fix (two-part):**
1. Do NOT warm-start CP-SAT from Singer elements — full_1's small-N analysis proves this biases
   search toward a structurally unrelated region. Instead, warm-start from the 105-mark
   Rokicki-Dogon set for k=106 attempts.
2. The right resource allocation for CP-SAT is either 4+ hours in a single extended run
   (outside the normal generation loop) or a different solver entirely (Gurobi, HiGHS, SCIP).
   Repeated 600s UNKNOWN runs are pure waste. The next generation should not schedule CP-SAT
   for k=103/104 — those are already covered by the Rokicki-Dogon database.

### [P4] MINOR — idea_005 (backtracking) has never been tested after 5 generations

**Evidence:** The gen 4 snapshot flags: "idea_005 (Backtracking with Pruning): Never tested.
last_confirmed_gen = 0." The gen005 agent_gaps synthesis lists this as gap #7 (though labeled
as gap #6 in the file). This has been flagged in gen 4 system_recommendations (Priority 3:
"archive idea_005 or test it") and apparently neither action was taken.

**Severity:** Minor in isolation, but represents a broader pattern: the pipeline accumulates
never-tested ideas that crowd the knowledge base and consume Architect attention without
contributing data. After 5 generations, an idea that has never been scheduled is either
not viable (and should be archived) or overlooked (and should be assigned).

**Fix:** The Architect should be instructed to either assign a test or explicitly archive
any idea with `last_confirmed_gen: 0` that has survived 3+ generations. The Consistency
Reviewer should enforce this.

## Missing Capabilities

### [MC1] CRITICAL — No extended-compute scheduling capability

The pipeline has no mechanism to schedule a 4-hour CP-SAT run. All agents run with
a 900s wall-clock timeout (3-phase with wrap-up). The highest-value next experiment
(CP-SAT k=106 with 105-mark warm-start, 4h+) cannot be executed in the current framework.

**Suggested fix:** The orchestrator should support an `extended_run` flag in `manifest.yaml`
that allows specific agents to bypass the normal timeout. Alternatively, the user can run
an extended CP-SAT script manually outside the loop — this should be documented as the
recommended path.

### [MC2] MODERATE — No helper for greedy extension from a given set

Every agent that tried to extend the 105-mark set had to reimplement the "can I add element x
to set S?" logic from scratch. A `greedy_extend(S, N)` helper that attempts to add more
elements to an existing set would have been immediately useful to 3-4 agents this generation.
The agent_gaps synthesis (gap #5) confirms this.

**Suggested fix:** Task the next experimentator with writing `helpers/extend.py` containing
`greedy_extend(initial_set, N, max_elements=None)`.

### [MC3] MODERATE — No remove-k/replace perturbation infrastructure

The 105-mark set is maximal — nothing can be added greedily. The only computational path
forward is remove-k elements and try to re-insert k+1 or more. This requires a
neighborhood search with a proper perturbation loop. No agent has a tested implementation
of remove-k with k≥3. Full_1's CP-SAT work covers the exact method; the perturbation
approach occupies the middle ground between greedy and ILP.

**Suggested fix:** Task an exploit or full agent with implementing remove-k perturbation
(k=2-8) using the 105-mark set as seed, with a budget of 10^6+ trials.

## Prompt Problems

### [PP1] MODERATE — Architect briefs name algebraic constructions without specifying formulas

As detailed in P2 above, the brief for explore_2 named "Bose-Chowla" without specifying
the correct formula or flagging the prior failed attempt. This is a recurring pattern:
gen 4 explore_2 also attempted invalid integer embeddings of group-theoretic constructions.

**Fix:** Add a section to `agents/architect.md` that requires: when assigning an algebraic
construction, the brief MUST include (a) the explicit formula, (b) a pointer to any prior
attempt, and (c) a note if the construction is equivalent to another tested approach.

### [PP2] MINOR — State of Affairs not updated before gen 5 ran

The `knowledge/state_of_affairs.md` still reflects gen 4 status (102-element plateau,
Rokicki-Dogon unverified). The gen 5 agents read this stale document. While this didn't
cause failures this generation (the Architect correctly briefed agents to fetch the database),
it means agents started with a pessimistic prior and some may have spent time re-deriving
things the SOA should have told them.

**Fix:** The Consistency Reviewer should run before gen 6 to update the SOA with the
gen 5 breakthrough. The orchestrator runs the Consistency Review every 3rd generation —
this is gen 5, so it may have run; but the SOA file should be checked.

## Knowledge Quality Issues

### [KQ1] MODERATE — idea_022 (Bose-Chowla AP) ambiguously describes Singer equivalence

The evaluator created idea_022 to document the "Bose-Chowla affine plane" construction
that gave 105. However, this is the same Bose-Chowla AP that explore_2 tried to implement
from scratch and got 312 violations. The knowledge base now has:
- idea_022: "Bose-Chowla AP — works, gives 105"
- (implicit in gen4 snapshot): "Ruzsa-type Bose-Chowla fails in integers"

Future agents reading idea_022 will not understand that there are two different formulas
going by similar names, and may attempt the broken naive formula again.

**Fix:** idea_022 should explicitly state: (a) the correct formula uses GF(q²+q+1) cyclic
group, (b) the naive formula i*p+(i²%p) is NOT the Bose-Chowla construction and fails for
large p, and (c) the correct formula is algebraically equivalent to Singer but using ap
instead of pp construction.

### [KQ2] MINOR — Pattern_012 labels 105 as "algebraic ceiling" but evidence is exhaustive-search-based

Pattern_012 states 105 is the algebraic ceiling. This is correct and well-supported
(experimentator_1 ran exhaustive multiplier search over all prime powers q≤109). The
pattern should document that the search was exhaustive (not just a best-effort attempt)
so future agents don't re-run the same search.

## Experiment Gaps

### [EG1] CRITICAL — Remove-k perturbation with k≥3 on 105-mark set untested

The 105-mark set is maximal under greedy extension. The next unexplored territory is
remove-k elements and attempt to re-insert k+1+. Experimentator_1 tested k=1,2 perturbation
(4000 trials) and found no improvement. k=3-10 perturbation (potentially millions of trials)
has never been run.

### [EG2] CRITICAL — No extended CP-SAT run has ever been attempted

All CP-SAT runs have been ≤600s per phase. The literature suggests Golomb ruler problems
of this scale may require hours or days for exact methods. A single 4h+ run on k=106
with the 105-mark set as warm-start has not been done.

### [EG3] HIGH — Alternative solvers (Gurobi, HiGHS, SCIP) never tested

CP-SAT (OR-Tools) is one solver. Gurobi with a trial license, HiGHS (free), or SCIP may
have better LP relaxations for this problem structure. Full_1 noted this in its recommendations.

### [EG4] MODERATE — Binary search on N for k=106 not attempted

Rather than asking "can we achieve k=106 in {0,...,10000}?", the question "what is the
minimum N where k=106 is feasible?" would give the solver a much easier problem and
reveal whether k=106 is achievable at all.

### [EG5] MODERATE — idea_005 (backtracking with pruning) never tested

After 5 generations. See P4 above.

---

## Overall Assessment

Generation 5 was strategically successful — the +3 breakthrough via Rokicki-Dogon is
significant — but operationally inefficient. One agent (explore_2) produced zero useful
output due to a brief ambiguity. Two agents duplicated the same data fetch. CP-SAT
received another round of inadequate compute.

The pipeline's strategic direction is now clear and undisputed: the only path to 106+
is computational search (CP-SAT with extended time, alternative solvers, perturbation
from the 105-mark base). The next generation should be focused and narrow, not
exploratory.
