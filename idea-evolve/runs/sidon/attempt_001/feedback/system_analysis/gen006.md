## 1. Pipeline Problems

### [CRITICAL] Research agent produced zero empirical output (gen 6 research_1)

**Evidence:** research_1's debrief explicitly states: "No WebSearch queries executed. No OEIS lookups performed. No papers downloaded or checked. Session terminated early." The F₂(10000) question has been open for **5 consecutive generations** (gens 2–6). Each research session has either failed to reach the web search phase or relied on training-data inference rather than live lookups.

**Root cause:** Research agents are allocated deep into their session flow before reaching the web search tasks. When sessions are cut short (timeout or context pressure), web searches are the first casualty. The brief does not enforce web search as the first action.

**Impact:** The single highest-information-value action in the pipeline (a 30-second OEIS lookup for A003022) has been deferred for 5 generations. If F₂(10000) = 105, all computational search is wasted. If F₂(10000) ≥ 106, CP-SAT efforts are correctly prioritized. Not knowing this costs the pipeline compute equivalent to several full CP-SAT runs.

### [CRITICAL] VLNS formulation bug identified but not fixed in-session

**Evidence:** full_1 debrief: "All 9 trials returned INFEASIBLE in <1 second... Likely bug: add_abs_equality domain conflict... Fix: create cross-diff variables with domain [0, N]." The fix is a 2-line code change. Each trial takes <1s. full_1 had time to fix and run 50+ trials but chose not to.

**Root cause:** Agent briefs prioritize "attempt multiple approaches" over "debug and iterate on a promising one." full_1 moved to Phase 3 (binary search on N) rather than fixing the bug in Phase 2.

**Impact:** VLNS is either the most promising near-term path (if bug is real) or the strongest evidence for k=106 infeasibility (if INFEASIBLE is genuine). We still don't know which after 9 trials. This is the highest-value unresolved question from gen 6.

---

### [MODERATE] CP-SAT helper requested for 2+ generations, still not built

**Evidence:** gen 5 full_1, gen 6 full_1, and gen 6 agent_gaps/gen006.md all request `helpers/cpsat.py`. gen 6 experimentator_1 created `rokicki_data.py` and `extend.py` but not the CP-SAT helper. The gen 6 VLNS formulation bug is directly related to re-deriving the CP-SAT formulation without a validated template.

**Root cause:** Architect has assigned the experimentator to helper creation tasks but not included the CP-SAT helper in scope. This is the third consecutive generation where the helper is requested but not prioritized.

**Impact:** Every full/exploit agent session re-derives CP-SAT constraints from scratch, wasting 5–10 turns on boilerplate. More critically, ad-hoc formulations introduce bugs (as seen in the VLNS INFEASIBLE case). A validated `helpers/cpsat.py` with correct difference variable formulation prevents this class of error.

### [MODERATE] Self-healing property not triggering a strategic pivot

**Evidence:** exploit_1 debrief: "Every k-element removal opens exactly k slots, which are always the removed elements." This is a mathematical invariant, not a probabilistic finding. The SoA from gen 5 still lists "remove-k (k=3-10) perturbation" as under-explored and high-priority. Gen 6 exploit_1 confirmed it for k=2-104 with 27K+ trials. The pipeline consumed a full exploit session to confirm what the addable-element structural analysis could have confirmed in minutes.

**Root cause:** The coverage map prioritized perturbation search without distinguishing between "empirical search" and "structural analysis." A structural analysis tool (implemented in gen 6 as part of exploit_1) should have been in the helpers library before perturbation search was assigned.

**Impact:** Minor at this point — the confirmation is now complete. But gen 7 should not assign any further perturbation-type exploit tasks for the 105-mark set.

## 2. Missing Capabilities

### [CRITICAL] No mechanism to verify agent tool usage

**Evidence:** research_1 produced findings entirely from training knowledge, presenting them as literature findings. There is no way for the evaluator or system critic to distinguish "agent actually searched the web" from "agent used training knowledge and wrote plausible-sounding findings."

**Impact:** Research agent outputs cannot be trusted as verified facts. The Ruzsa–Lindström construction, GRASP, tabu search proposals — all from training data, not from actual web search. The pipeline is making strategic decisions based on unverified claims.

**Recommendation:** Research briefs should require agents to include URLs or paper titles with page numbers for any factual claim. Claims without citations should be labeled "unverified (training data)."

---

### [HIGH] No C-extension for inner-loop sidon operations

**Evidence:** Multiple agents across multiple generations cite Python speed as a blocker:
- exploit_1 gen6: "reimplemented diff-checking logic inline for ~200 trials/second. A C extension would give 10-100x speedup."
- explore_1 gen6: "Systematic 2-opt (needs C implementation): needs ~10-20min in C."
- full_1 gen5 and gen6: CP-SAT formulation overhead in Python.

**Impact:** The effective trial budget for perturbation search is ~200/s in Python vs ~20,000/s in C. This is a 100x handicap on the most compute-intensive path (perturbation).

---

### [MODERATE] No anti-algebraic CP-SAT experiment

**Evidence:** explore_1 gen6 suggests "CP-SAT with constraint that solution shares ≤50% elements with 105-mark set." Architect gen6 report lists "Anti-algebraic CP-SAT" as something that "didn't fit." This idea has been mentioned in 2+ generations without being assigned.

**Impact:** All CP-SAT runs warm-start from or near the algebraic construction. The small-N analysis (gen5) shows optimal sets share only ~8% of elements with Singer. If this generalizes, we may be searching the wrong region.

## 4. Resource Issues

### [MODERATE] CP-SAT compute allocated without formulation validation

**Evidence:** full_1 gen6 ran CP-SAT k=106 for 1800+ cumulative seconds (1200s + 600s) while also running a buggy VLNS that returned INFEASIBLE in <1s. 80% of the session's compute went to "UNKNOWN" CP-SAT with no diagnostic value added over previous runs.

**Root cause:** CP-SAT with "UNKNOWN" status adds zero information per additional second beyond the first UNKNOWN. The pipeline needs a decision rule: "If CP-SAT returns UNKNOWN with the same formulation as last run, do not allocate more CP-SAT with the same formulation."

**Recommendation:** Add to the full/exploit agent brief: "If CP-SAT returns UNKNOWN with the same formulation as a previous session, do NOT run it again with the same settings. Try a different formulation or solver."
