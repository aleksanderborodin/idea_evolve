### EXP-1: Combined Recipe End-to-End (idea_013) — CRITICAL

**What to test:**
1. `CayleyGraph` construction (same instance for all steps — hasher compatibility)
2. BFS to depth 6: `bfs_result = graph.bfs()` → 19.4M states with exact distance labels
3. Extract training data: `X = bfs_result.layers[0..5]` flattened, `y = distance_from_solved`
4. Train embedding MLP: `Embedding(120, 32) → Linear(32*120, 512) → ReLU → Linear(512, 1)`. MSE loss, 10 epochs, learning_rate=1e-3
5. Wrap in Predictor: `predictor = cayleypy.Predictor(graph, model)`
6. Beam search: `graph.beam_search(initial_state, beam_width=4096, max_steps=80, predictor=predictor, bfs_result_for_mitm=bfs_result, beam_mode='simple')`
7. Combine with compression fallback (44114 baseline) for puzzles beam search can't improve

**Rationale:** All four components individually verified by research_1 (gen003). This is the single strongest hypothesis for beating 44114. After 3 generations of circling this experiment, it must be executed.

**Hypothesis:** The embedding predictor trained on exact BFS data, combined with MITM backstop, will significantly outperform the raw integer MLP on random walks (which only saved 20 moves). Expected range: 35000-40000 (optimistic), 43000+ (pessimistic).

**Expected information gain:**
- If successful (beats 44094): Confirms the combined recipe as the primary path. Next step: scale beam width, tune embedding dim, increase MITM depth.
- If marginal (44000-44094): The predictor approach has limited juice. Need fundamentally different paradigm (GNN, RL, Kaggle solution analysis).
- If fails (≥44114): The beam search + predictor paradigm is dead. Must pivot to completely different approaches.

**Time estimate:** 15-20 minutes GPU time (BFS: 1s, training: 2-3 min, beam search: 10-15 min for 101 puzzles).

**Assigned to:** One full-type or explore agent with milestone protocol.

### EXP-2: Embedding Architecture Isolated Test — HIGH

**What to test:**
1. Train embedding MLP on BFS depth-6 data (same as EXP-1 steps 1-4)
2. Run beam search on just 5 puzzles (sids 10, 50, 100, 200, 500) with embedding predictor
3. Run beam search on same 5 puzzles with raw integer MLP predictor (same training data)
4. Compare path lengths directly

**Rationale:** Isolates the architecture variable. research_1 showed 5.3x loss reduction in controlled training experiment, but we don't know if better loss translates to better beam search outcomes. This A/B test quantifies the architecture impact on actual solving performance.

**Hypothesis:** Embedding predictor will find shorter paths than raw integer predictor on the same puzzles, especially on deeper puzzles (sid 200, 500) where the predictor needs to generalize beyond training depth.

**Expected information gain:** Quantified architecture impact. If embedding predictor is 2x+ better on beam search success rate, the architecture fix is validated and all future predictor experiments should use it.

**Time estimate:** 10 minutes (training: 3 min × 2 architectures, beam search: 5 min × 2 × 5 puzzles).

### EXP-3: BFS Training Data vs Random Walk Training Data — HIGH

**What to test:**
1. Train the same embedding MLP on: (a) BFS depth-6 exact data (19.4M samples), (b) random walks depth-20 (800k samples, BFS mode), (c) combined (BFS + random walks)
2. Evaluate each on beam search success rate across depth buckets

**Rationale:** idea_010 claims BFS data is strictly superior to random walks. But BFS data only covers depths 0-6, while puzzles range to depth 1000. Random walks cover deeper states (depth 20) but with noisy labels. The comparison determines whether exact-but-shallow training beats noisy-but-deeper training.

**Hypothesis:** BFS data will produce a better predictor for puzzles with depth ≤ 100 (within a few BFS radii of the training distribution). For depth 500+ puzzles, random walk data may be better because it covers states closer to the puzzle's actual depth.

**Expected information gain:** Determines optimal training data strategy. If BFS dominates, all future training uses BFS. If random walks are better for deep puzzles, a depth-stratified training approach is needed.

**Time estimate:** 15 minutes (3 training runs × 3 min each, beam search evaluation × 3).

### EXP-4: Scramble Structure Exploitation for Shallow Puzzles — HIGH

**What to test:**
1. For puzzles with sid 1-20 (depth ≤ 20): attempt to find paths shorter than sample_submission by reversing suffixes of known scrambles
2. Use `MeetInTheMiddle.find_path_between()` for optimal bidirectional solving on these shallow puzzles
3. Compare to current compression baseline on the same puzzles

**Rationale:** This is the lowest-risk unexplored direction. The brief noted that scramble_depth == initial_state_id, meaning for shallow puzzles (sid 1-20), the optimal path is at most the depth. sample_submission already gives paths of length == depth for these puzzles, but there may be shorter paths since the generators aren't minimal (each generator is a 5-cycle, so a depth-5 scramble might be solvable in fewer moves via non-generator moves).

**Hypothesis:** For puzzles with sid ≤ 10, `MeetInTheMiddle.find_path_between()` will find paths equal to or shorter than sample_submission. This won't significantly impact total fitness (these puzzles are ~0.3% of score) but validates the tooling for harder puzzles.

**Expected information gain:** Whether MITM bidirectional search works in practice for any puzzle depth. Also tests whether scramble_depth == id means the path IS optimal or just upper-bounds it.

**Time estimate:** 5 minutes (MITM on 20 shallow puzzles).

### EXP-5: Beam Width Scaling with Correct Predictor — MEDIUM

**What to test:**
- Same pipeline as EXP-1, varying beam_width: [1024, 2048, 4096, 8192, 16384]
- Record per-puzzle: path length, solve rate, wall-clock time, GPU memory usage
- Test on 10 puzzles spanning all depth buckets

**Rationale:** Previous beam width experiments (gen001/gen002) used unguided or hamming-predictor beam search. The correct predictor (embedding + BFS data) changes the cost-benefit calculus — a good predictor may allow smaller beams to outperform large unguided ones.

**Hypothesis:** With the embedding predictor, beam_width=4096 will match or beat unguided beam_width=32768. The predictor makes the search smarter, reducing the need for brute-force width.

**Expected information gain:** Calibrated beam parameters for the correct predictor. Saves future iterations from parameter sweeps.

**Time estimate:** 20 minutes (5 beam widths × 10 puzzles × ~2 min each).

### EXP-6: MITM Depth Sweep — MEDIUM

**What to test:**
- Same pipeline as EXP-1, varying MITM depth: [0, 4, 5, 6]
- Measure how much the MITM backstop helps at each depth
- Test on a fixed set of 10 puzzles across depth buckets

**Rationale:** MITM depth 6 produces 19.4M states and takes 1s. Depth 7 OOMs. But we don't know the marginal value of each MITM level. Depth 0 (no MITM) vs depth 4 vs depth 6 quantifies the backstop contribution.

**Hypothesis:** MITM provides a fixed-depth optimal backstop — any puzzle within 2×MITM_depth of solved gets an optimal path. For depth 6, this covers puzzles up to depth 12 optimally. Beyond that, MITM is less helpful.

**Expected information gain:** Whether MITM is worth the memory cost at production scale, and the optimal depth within memory constraints.

---

### EXP-7: Embedding Dimension Sweep — MEDIUM

**What to test:**
- Train embedding MLPs with embed_dim = [8, 16, 32, 64]
- Measure: training loss, inference memory during beam search, beam search success rate
- Fixed architecture: Embedding(120, dim) → Linear(dim*120, 512) → ReLU → Linear(512, 1)

**Rationale:** research_1 tested only dim=32. Smaller embeddings use less GPU memory during beam search inference (critical for large beam widths). Larger embeddings may capture more structure but risk overfitting on shallow BFS data.

**Hypothesis:** dim=16 is sufficient for the permutation structure and uses 2x less memory than dim=32. dim=64 overfits on depth-6 BFS data.

**Expected information gain:** Optimal embedding dimension for memory vs accuracy tradeoff.
