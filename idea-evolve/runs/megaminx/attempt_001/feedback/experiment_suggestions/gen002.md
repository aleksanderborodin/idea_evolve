### EXP-1: Trained MLP Predictor End-to-End (CRITICAL)

**What to test:**
1. Generate training data: `graph.random_walks(width=50000, length=20, mode='bfs')`
2. Train a 3-layer MLP: `120 → 256 → 128 → 1`, MSE loss, 10 epochs
3. Run `beam_search(predictor=predictor, beam_width=4096, max_steps=80, beam_mode='simple')` on hard and very_hard proxy puzzles
4. Compare to 44114 compression floor

**Rationale:** idea_008 has 0 central uses after 2 generations. This is the primary path to the target. Every generation without a trained-predictor result is a wasted generation.

**Hypothesis:** A trained predictor will guide beam search toward shorter paths than compression alone can find. The key question: does the predictor learn graph distance well enough to beat 44114?

**Expected information gain:** If successful → new best score, path to target clarified. If it fails to beat 44114 → we know the predictor architecture/training is insufficient and need a different approach (different architecture, more training data, different training distribution).

**Time estimate:** 10-15 minutes on GPU (research_1 confirmed ML pipeline is fast enough).

**Assigned to:** experimentator_1 (primary) or exploit_1 (fallback)

### EXP-2: Compression + Beam Search Combination (HIGH)

**What to test:**
1. Apply explore_2/sol01's 336 empirical identity rules to compress sample_submission paths (compression_ratio → 0.8723)
2. Use compressed paths as starting states for beam search
3. Compare: pure compression (44114) vs compression-then-beam (???)

**Rationale:** Compression gets paths to 0.8723 ratio. Starting from already-short paths makes beam search's job much easier — the search space is smaller. This is the most promising order of operations and no agent has tried it.

**Hypothesis:** Beam search starting from compressed paths will find shorter paths than either pure beam or pure compression. The compressed starting point is closer to the optimum, so beam search can reach it in fewer steps.

**Expected information gain:** Whether the combination beats 44114. If it does, we know the order-of-operations matters. If it doesn't, we know beam search needs a better predictor, not a better starting point.

### EXP-3: Beam Width Scaling with Trained Predictor (MEDIUM)

**What to test:**
- Same pipeline as EXP-1, varying beam_width: [1024, 2048, 4096, 8192, 16384]
- Record per-puzzle: path length, solve rate, wall-clock time
- Identify optimal beam width for each depth bucket

**Rationale:** research_1 found beam_width must be 4x-32x larger than gen001 used for hamming/unguided. With a trained predictor (which is actually informative), the optimal beam width may be smaller — the predictor prunes bad paths, reducing the beam width needed.

**Hypothesis:** Trained predictor + beam_width=2048 will match or beat unguided beam_width=32768, because the predictor makes the search smarter, not just wider.

**Expected information gain:** Calibrated beam parameters for the trained-predictor approach. Saves future iterations from parameter sweeps.

---

### EXP-4: Training Data Depth Generalization (MEDIUM)

**What to test:**
1. Train predictors on single-depth distributions: depth = [10, 15, 20, 30, 50]
2. Evaluate each on puzzles across ALL depth ranges
3. Measure: does depth-matched training generalize? Is domain randomization needed?

**Rationale:** The proxy has depth 1-1000. Training on depth-20 walks is convenient but may not generalize to depth-500+ puzzles. We need to know whether depth-20 is "good enough" or whether training on a wider distribution is required.

**Hypothesis:** A predictor trained only on depth-20 walks will perform poorly on depth-500+ puzzles (distribution shift). A predictor trained on mixed depths (10-50) will generalize better.

**Expected information gain:** Whether the approach is fundamentally limited by distribution mismatch, or whether depth-20 training is sufficient.
