# Experiment Suggestions — Gen 004

## Priority 1 (MUST DO in gen005)

### EXP-1: Updated recipe — path-intermediate training + MlpModel + beam_width=65536

**Hypothesis:** The predictor fails on hard/very_hard puzzles because training data only covers depth 0-50. Path-intermediate data from compressed paths covers depth 1-888. Combined with MlpModel (proven architecture) and beam_width=65536 (16× increase), this should produce a meaningful improvement.

**What to test:**
1. Extract (state, remaining_depth) pairs from all 101 compressed paths (~44K samples)
2. Train `MlpModel(graph, hidden_dims=[512, 256])` on this data
3. Run `graph.beam_search(predictor=predictor, beam_width=65536, batch_size=2048, bfs_result_for_mitm=bfs_result)`
4. Fall back to compression for failed puzzles

**Expected information gain:** If score < 43000: the beam search paradigm works at sufficient scale. If score > 44100: training data depth alone is insufficient and we need a fundamentally different approach. Either result is highly informative.

**Beam mode variant:** Run the same experiment with `beam_mode='advanced'` (non-backtracking, no MITM) as sol02. Compare head-to-head.

### EXP-2: Beam width sweep on a fixed puzzle subset

**Hypothesis:** Solution quality scales log-linearly with beam width (pattern_009, from CayleyPy paper). We need to verify this on Megaminx specifically.

**What to test:**
1. Select 7 puzzles: one from each depth bucket (sid ~10, ~50, ~100, ~200, ~500, ~700, ~1000)
2. For each puzzle, run beam search at beam_width = [4096, 8192, 16384, 32768, 65536]
3. Use MlpModel + path-intermediate training as the predictor
4. Record: path length achieved, time taken, OOM occurrence
5. Plot path_length vs log(beam_width)

**Expected information gain:** Determines the optimal beam_width for our hardware. Identifies where the log-linear relationship breaks down (if it does). Quantifies the marginal value of each beam_width doubling. If the curve is flat above 8192, we save compute; if it's still improving at 65536, we know to push further.

## Priority 2 (SHOULD DO in gen005)

### EXP-3: Non-backtracking vs MITM head-to-head

**Hypothesis:** Non-backtracking (idea_015) provides more benefit than MITM (idea_012) for deep puzzles because it prunes the entire search tree vs saving only 6 BFS layers.

**What to test:**
1. Use the same trained predictor (from EXP-1)
2. On the same 7-puzzle subset, run:
   - (a) `beam_mode='simple'` + `bfs_result_for_mitm=bfs_result` + beam_width=W
   - (b) `beam_mode='advanced'` (no MITM) + beam_width=W
   - (c) `beam_mode='simple'` (no MITM, no non-backtracking) + beam_width=W (control)
3. Use W=16384 (compromise between compute cost and effectiveness)
4. Compare path lengths per puzzle and overall

**Expected information gain:** Determines which mode to use for production solutions. If non-backtracking wins: use advanced mode and skip BFS computation entirely (saves time). If MITM wins: keep BFS + simple mode. If neither helps: the predictor is too weak for any beam search mode to help on deep puzzles.

### EXP-4: Long random walks (depth 200) as training data

**Hypothesis:** Random walks at depth 200 provide noisier but deeper training signal than depth-50 walks, improving predictor accuracy on hard puzzles (depth 101-300).

**What to test:**
1. Generate `graph.random_walks(width=10000, length=200, mode='bfs')` → ~2M samples covering depths 0-199
2. Train MlpModel on this data
3. Compare predictor MAE at depth 50, 100, 150, 200 against the path-intermediate predictor
4. Run beam search on hard-puzzle subset (sids 101-300)
5. Compare path lengths vs EXP-1's path-intermediate approach

**Expected information gain:** Tells us whether random walk depth matters more than data quality. If depth-200 walks beat depth-50 but lose to path intermediates: confirms path intermediates are the right data source. If depth-200 walks beat path intermediates: random walk noise is beneficial (regularization effect).

## Priority 3 (NICE TO HAVE)

### EXP-5: Training data depth ablation

**Hypothesis:** Training data covering depth 100-300 is more important than depth 0-50 for improving the hard bucket (23.9% of score).

**What to test:**
1. Filter path-intermediate training data to different depth ranges:
   - (a) All depths (1-888)
   - (b) Depth 1-50 only (equivalent to current random walk coverage)
   - (c) Depth 50-300 only (hard puzzle range)
   - (d) Depth 300-888 only (very_hard range)
2. Train separate predictors on each
3. Run beam search on the full proxy set
4. Compare per-bucket fitness

**Expected information gain:** Identifies which depth range of training data is most valuable. If depth 50-300 is most important: agents should focus training data collection there. If all depths are needed: full path intermediates are the right approach. If depth 300+ is most important: the predictor mainly helps on very_hard puzzles.

### EXP-6: Batch size × beam width memory profiling

**Hypothesis:** beam_width=65536 with batch_size=2048 is feasible on 16 GB GPU with MlpModel (one-hot encoding). research_1 calculated ~300 MB per batch.

**What to test:**
1. Train MlpModel on path-intermediate data
2. Run beam search at beam_width=65536 with batch_size=[512, 1024, 2048, 4096]
3. Monitor GPU memory usage (nvidia-smi or torch.cuda.memory_allocated)
4. Record: peak memory, time per step, OOM events

**Expected information gain:** Determines the maximum feasible beam_width on our hardware. If 65536 works at batch_size=2048: proceed with confidence. If OOM: find the actual ceiling and work within it. This is a prerequisite for EXP-1 and EXP-2 — we need to know the hardware limits before committing to large beam widths.

---

### EXP-7: Predictor accuracy evaluation at different depths

**Hypothesis:** The predictor's MAE increases dramatically beyond its training data depth range, explaining why beam search guidance fails on deep puzzles.

**What to test:**
1. Train predictor on path-intermediate data
2. Generate test states at known depths (10, 50, 100, 200, 500, 800) using BFS or random walks
3. For each depth, compute: MAE, RMSE, correlation between predicted and true distance
4. Plot predictor error vs depth

**Expected information gain:** Pinpoints where the predictor breaks down. If error is low up to depth 300 but explodes after: beam search can help hard puzzles but not very_hard. If error is uniformly low: the predictor is fine and the beam_width is the bottleneck. If error is high everywhere: the training data or model is fundamentally insufficient.
