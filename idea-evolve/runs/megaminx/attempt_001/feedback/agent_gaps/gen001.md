# Agent Gaps — Gen 001

## Knowledge Gaps

### 1. Predictor pipeline not implemented by any solution agent

**Observation:** research_1 confirmed that cayleypy's full ML pipeline works in this environment:
- `Puzzles.megaminx()`, `graph.random_walks()`, `Predictor(graph, model)`, `beam_search(predictor=...)` all confirmed working
- Training loop verified: MSE 3.46 → 0.86 in 3 epochs on 1000 samples

Yet no solution agent implemented predictor-guided beam search. All explore and full agents focused on cancellation and unguided beam search, which are confirmed dead ends.

**Likely cause:** The `cayleypy_beam_solver` helper in `helpers/core.py` does NOT expose the `predictor` kwarg. Agents using the helper cannot access predictor-guided search without calling cayleypy API directly. This is a friction point — agents may not have known to call the API directly.

**Recommended fix:** Either (a) update the helper to expose predictor, or (b) ensure agents know to use the cayleypy API directly.

### 2. Beam search failures were not diagnosed

Multiple agents tried beam search (explore_2_sol05, full_1) and found it didn't beat compression. But none added instrumentation to understand WHY — was beam search returning None? Longer paths? Paths that failed validation? Without diagnosis, agents couldn't learn from the failure.

**Gap:** No solution logged beam_search return values vs compression baselines in a way that would help future agents understand the failure mode.

### 3. No per-puzzle analysis of where compression help vs hurt

The overall compression_ratio (0.9158) was reported, but no agent analyzed WHICH puzzles benefited most from compression and WHICH still had headroom. The very_hard bucket (50 puzzles) is where the score is — understanding compression's limits there would guide where to focus search effort.

## Pipeline Gaps

### 4. cacleypy_beam_solver helper doesn't support predictor kwarg

The helper function at `helpers/core.py:cayleypy_beam_solver()` wraps `graph.beam_search()` but only accepts `beam_width` and `max_steps`. The `predictor` kwarg is not exposed.

Agents using the helper (as recommended in `description.md`) cannot implement predictor-guided search without bypassing the helper entirely.

**Status:** Confirmed by research_1 debrief: "The `cayleypy_beam_solver` wrapper in helpers/core.py doesn't support the `predictor` kwarg — it only passes `beam_width` and `max_steps`. For the ML approach, agents must call the cayleypy API directly rather than through the helper."

**Recommendation:** Add `predictor` kwarg to `cayleypy_beam_solver`, or create a new `guided_beam_solver(state, model, beam_width, max_steps)` function as research_1 suggested.

### 5. helpers/README.md has wrong PROXY_SIZE

The README says `PROXY_SIZE = 100` but `helpers/core.py` and `description.md` both correctly say 101. This inconsistency was noted by multiple agents and could cause confusion.

**Recommendation:** Fix `helpers/README.md` to say 101.

### 6. initial_facts.md has conflicting hardware descriptions

One block describes GPU + MPS parallelism; another block says CPU-only. Architect noted this in their report. Agents following the wrong block might make incorrect assumptions about hardware capabilities.

**Recommendation:** Clean up `initial_facts.md` hardware section to be unambiguous.
